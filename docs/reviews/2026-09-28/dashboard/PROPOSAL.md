# Dashboard 重做提案：一棵树、五列、四问

2026-09-28｜状态：**提案，未采用**。前提是同日已采用的骨架（生态为根、主题为列、目标由因子生成）、部件重切（bom.json 2.0）与生成式目标表（tco_targets.json 2.0）。本稿不谈样式，只谈 dashboard 的推导逻辑；用户审定后再做页面。

## 0. 一页结论

- dashboard 是四段（采集 → 事实 → 规则 → 视图）的第四段，它没有自己的逻辑，只能继承前三段的逻辑。所以 dashboard 的结构必须等于对象模型的结构，不能另起一套"话题"。
- 对象模型只有一棵树：**数据中心 → 八个生态 → 部件 / 站点权利**。dashboard 的每一屏就是这棵树上的一个节点，首页是根。
- 每个节点用同一套**五列**描述：构成、运行、价格、时间、主体（五类变量）。根节点的五列就是那本账，部件节点的五列就是它自己的规格、效率、价格、交期、供应商。
- 每一屏固定回答**四问**，四问就是四段倒过来：它值多少（事实）、它由什么组成（树）、它怎么影响账（规则 = 因子）、数据从哪来缺什么（采集 = 目标表）。
- 首页因此只有三块：账（三级：成本、收入、回报）、8 × 5 矩阵（生态 × 五类变量，每格一个数和一个数据状态色）、最近变化。没有别的面板。
- 现有页面不删功能，重新归位：经济模型、成本、TCO 三个计算器成为根节点"价格"列的展开；爆炸图与 3D 成为"由什么组成"一问的视觉形式；研究工作台成为部件节点"它是什么"的深读；供应中心成为"数据从哪来"的全局视图；`index.html` 的 KPI 拼盘退役。

## 1. 旧 dashboard 为什么没有逻辑

| 页面 | 现在回答的问题 | 问题所在 |
|---|---|---|
| index.html | 一组行业 KPI + 入口卡片 | KPI 是挑出来的，挑选标准没有登记；换一个人会挑另一组 |
| economics.html | 一座数据中心四本账 | 是计算器，不是导航；它的输入从哪来、缺什么，页面上看不到 |
| cost.html / tco.html | 两套成本计算 | 与 economics 三套并存，读者不知道该信哪一套 |
| bom.html / bom3d.html | 拆解到部件 | 拆解完停在部件档案，回不到账 |
| research.html / report.html | 按对象或按模块深读 | 与账、与部件之间没有链接 |

共同病根：每个页面各答一个问题，页面之间没有一条推导链。读者从账追不到部件，从部件追不到数据缺口，从数据缺口回不到账。

## 2. 底层逻辑：从已采用的骨架推出来

已经采用的东西只有这些，dashboard 不能用它们以外的概念：

1. 三级：成本、收入、回报——账的三行。
2. 四段：采集 → 事实 → 规则 → 视图——数据的四道工序，严格有序。
3. 五类变量：构成、运行、价格、时间、主体——描述任何对象的五个正交维度。
4. 六队：采集的分工——只出现在"数据从哪来"里。
5. 一棵树：数据中心 → 八生态 → 部件（61 + 软件 1 + 基型 1）与站点权利（6）。
6. 九主题：一个部件节点的研究提纲，是节点内部的深度，不是导航层。
7. 因子树：24 个因子，从公式往下推到部件；它是"规则"这一段的具体形态。
8. 目标表：287 行，由因子、部件、权利生成；它是"采集"这一段的具体形态。

把它们放在一起，结构只有一种拼法：

```
树的节点（1 → 8 → 69）                     ← 导航：一屏一个节点
    × 五列（构成 运行 价格 时间 主体）        ← 每屏的横轴：五类变量
    × 四问（事实 组成 规则 采集）            ← 每屏的纵向面板：四段倒序
```

- **一棵树**决定"看哪个对象"。
- **五列**决定"从哪个维度看"。五列在每一级都成立：根的价格列是每 MW 资本开支与年成本，生态的价格列是该系统的每 MW 造价，部件的价格列是它的单价。
- **四问**决定"这一屏放什么"。四问不多不少：多一问就是四段以外的东西，少一问链就断了。

九主题不是第四个轴：它是部件节点"它是什么"一问展开后的目录。六队也不是轴：它是"数据从哪来"一问里的分组。

## 3. 每一级节点的五列怎么算（聚合规则）

规则登记为数据（`framework/dashboard_rules.json`，属第三段"规则"），页面只读取，不在 JS 里写公式。

| 列 | 部件节点（自己的值） | 生态节点（从部件聚合） | 根节点（那本账） |
|---|---|---|---|
| 构成 | 规格、每柜数量、装在哪个尺度 | 部件数、占机柜功率份额 | IT 容量 MW、GPU 数、代际 |
| 运行 | 效率、功耗、利用率 | 系统效率（冷却 → PUE 贡献，计算 → 利用率） | PUE、负载率、付费利用率 |
| 价格 | 单价、价格序列 | 每 MW 造价（因子树 capex 分线之和） | 每 MW 资本开支、年成本、收入、回报 |
| 时间 | 交期、寿命 | 关键路径：部件交期取最大 | 建设周期、折旧年限、租约期限 |
| 主体 | 供应商名单、集中度 | 供应商数、单一来源部件数 | 业主、租户、融资方、电力与土地权利方 |

每一格的来源固定为三种之一：价格库序列、指标、或因子树公式；来源写在规则文件里。没有来源的格显示"缺"，不显示估计值。

## 4. 首页 = 根节点

```
┌ 账（三级）───────────────────────────────────────────────┐
│ 成本 $/MW·年   收入 $/MW·年   回报 ROIC      情景：当前基准 │
├ 8 × 5 矩阵（生态 × 五类变量）──────────────────────────────┤
│           构成      运行      价格        时间      主体     │
│ 设施      ·        ·        $x/MW      ·        ·        │
│ 电力      ·        ·        $x/MW      30 月     ·        │
│ 冷却      ·        PUE 贡献  $x/MW      ·        ·        │
│ 计算      GPU/MW   利用率    $x/MW      交期      集中度    │
│ 内存      ·        ·        ·          ·        ·        │
│ 存储      ·        ·        ·          ·        ·        │
│ 网络      ·        ·        ·          ·        ·        │
│ 控制软件   ·        ·        订阅价      ·        ·        │
│ 站点权利   ·        ·        地价       排队年限   持有方    │
├ 最近变化 ───────────────────────────────────────────────┤
│ 新事实（序列新点）· 新事件（inews）· 到期目标（目标表）        │
└─────────────────────────────────────────────────────────┘
```

- 矩阵每格：一个数（或"缺"）+ 数据状态色（sourced / assumed / needed，来自该生态该列对应的目标行）。点格进入生态节点并停在那一列。
- 矩阵就是数据缺口热图：今天 287 行目标里 246 行 needed，矩阵会大面积灰，这是事实，也是采集的任务书。
- 站点权利作为第九行：它们不是部件，但有价格、时间、主体三列。

## 5. 三层页面的形状（同一个模板）

每一屏四个面板，顺序固定：

1. **它值多少**：该节点五列的现值、时点、来源等级。部件节点在此展开九主题目录（研究深读入口）。
2. **它由什么组成 / 属于什么**：子节点表（行 = 子节点，列 = 五列缩略），父节点链接。根 → 八生态 + 站点权利；生态 → 部件；部件 → 无子节点，显示装配关系与 3D 入口。
3. **它怎么影响账**：该节点喂的因子、因子公式、账里的敏感度排名。部件节点显示"这个部件的价格变 10%，每 MW 资本开支变多少"。
4. **数据从哪来，缺什么**：该节点的目标行按六队分组，状态色与下次到期；最近事件（inews 事件卡按部件、生态映射）。

同一个模板意味着一个页面 `node.html?id=<root | ecosystem:x | part:x | site:x>`，首页是它不带参数的形态。
