# 数据中心行业研究架构：问题、证据、任务与长期学习设计

日期：2026-09-06。性质：只读审阅后的设计建议；没有修改仓库、导入资料或启动持续任务。下文行业分类用于研究架构，不代表已经完成外部行业事实核验。附件和旧框架均作为可重新评价的分析对象。

## 1. 首要判断：保留研究资产，重新划清几个不同维度

现有 15 模块是有用的编辑分工和报告导航，却不能严格称为行业知识的 MECE 分解。它把对象、角色、地域、分析视角和综合层放在同一级：M06/M07/M08 是技术系统，M02/M03 是交易两侧，M11 是经济视角，M14 是地域切片，M15 是综合分析。框架自己写明 M14 平行运行 M01–M13，却同时要求每个事实只能归一个模块；这在知识引用上互相冲突。[框架总览](/Users/m5/code/inresearch.ai/framework/00_overview.md:3) [三维与横切维度](/Users/m5/code/inresearch.ai/framework/00_overview.md:10) [M14 平行定义](/Users/m5/code/inresearch.ai/framework/00_overview.md:48)

“只有 M15 可以跨模块引用结论”也不适合工程研究：选址必须引用供电结论，冷却必须引用服务器功率和负载条件。M05、M08 的实际定义已经这样做了。[M05](/Users/m5/code/inresearch.ai/framework/modules/M05_土地与区域.md:6) [M08](/Users/m5/code/inresearch.ai/framework/modules/M08_散热与制冷.md:5) 正确约束应是“同一事实保留一个身份、每项维护责任有主负责人，允许多个问题与视图引用”，而不是禁止知识跨界。

旧重心明显是 AI 扩张与投资周期：全景报告把 200GW 能否实现、瓶颈、转情景信号列为终极问题，M04–M10 被要求回答会不会卡住 200GW。[项目全景](/Users/m5/code/inresearch.ai/docs/PROJECT_PANORAMA.md:17) [固定逻辑](/Users/m5/code/inresearch.ai/framework/00_overview.md:44) 这可以保留为一个重大研究专题，但不能继续充当“成为数据中心行业专家”的唯一目标。12–18 个月领先关系也应列为待验证假设，不能在方法论层预先规定为真。

新版目标建议明确为六种可检验能力：能解释系统原理；能算清关键量及边界；能比较架构和供应商；能诊断失效与约束；能把技术、运营与商业关系贯通；能对未来提出有期限、可回测的判断。材料多少、3D 精美程度、Finding 数量只能说明工作量，不能替代这六种能力。

## 2. 底座：对象与关系统一，多视角展开

建议采用“对象—关系—问题—证据—结论—交付”六类登记。先用现有 JSON/Markdown 完成契约即可，不必先更换数据库。关系结构成熟后再决定是否需要图数据库。

### 2.1 必须分开的对象

| 对象类别 | 示例与边界 | 重要约束 |
|---|---|---|
| 概念与系统类型 | 配电系统、CDU、服务器、调度器、推理服务 | 表示某一类东西，不承载所有厂商产品的混合参数 |
| 产品型号与版本 | 某型号、固件版本、特定配置 | 参数、测试结果必须带版本与配置，不能只挂产品线 |
| 物理实例 | 某站点、分期、楼宇、机柜、设备实例 | 同一园区多期不能因公司或租户不同重复计容量 |
| 组织及其业务角色 | 制造商、开发商、业主、运营商、租户、融资方 | 同一公司允许多个角色，角色需关联对象与时间 |
| 流程、工作负载与服务 | 建设、调试、运维；训练、推理、通用计算、存储服务 | 业务需求、运行行为和设备类型不可混为一个分类 |
| 地域、制度与事件 | 辖区、标准版本、政策生效、停电、产品退出 | 时间与适用范围显式登记，不能把地域当独立重复数据库 |
| 合同与经济关系 | 买卖、租赁、电力供应、融资、服务承诺 | 付款方、收款方、权利义务、交付对象与期间分别记录 |
| 证据对象 | 文献作品、文档版本、实际文件、表格、原始数据、测试记录 | 文献身份、发布版本、文件哈希分别登记，路径不是身份 |

## 5. 每个研究节点的契约

节点是“研究入口”，不是一个资料文件夹。适用性可以不同，但下面十二项必须有值或明确说明不适用/未知。

1. **身份与边界**：稳定 node_id、类别、规范名、别名、定义、包含/排除项、类型与实例区别、版本。
2. **关系与位置**：物理 parent/组件、供电/冷却/连接、上下游、角色关系；每条关系标明是类型关系还是实例关系。
3. **功能与原理**：解决的问题、输入输出、核心机制、最低前置知识。
4. **接口与条件**：尺寸、电气、热、流体、协议等适用接口；环境、工作负载、配置及限制条件。
5. **研究问题**：稳定 question_id、问题类型、范围、关键程度、当前答案、依赖问题、所需证据。
6. **指标与口径**：哪些量适用、单位/分母/时段/阶段/负载/边界；定义、规范值、实测、估算、预测分别存放。
7. **证据与争议**：原始出处、版本和页表位置；原始数据来源族；支持/反驳关系；不确定性及失效条件。
8. **型号、案例与对照**：代表产品或真实项目、已知替代路线；不要用一个样例默认为行业普遍规律。
9. **计算或验证**：可复算公式/脚本、输入 fact_id、环境与结果，或适合该问题的检查步骤。
10. **材料入口**：与节点及具体问题相连的原理、规范、产品、实测、案例、市场资料；区别待读、已读、已采用。
11. **缺口与维护责任**：未知原因、下一任务、负责人/复核人、更新时间、到期或事件触发规则。
12. **可交付物**：解释卡、接口图、比较表、案例、模型、Finding；3D geometry_id、细节层次与研究状态单独登记。

每个节点只需维护一份规范登记，各视角和 3D 卡片读取同一份。对公司、政策等非物理节点，物理接口或 3D 坐标可明确 N/A；不应为“表格齐全”编造字段。3D 细化一个重要部件时，同时给它定义、关系、最少一组关键问题和材料入口；可以先显示未知状态，不能把“有模型”表示为“已研究”。

**例：CDU 节点的一个限定问题。**“在指定服务器/机柜配置、进水条件及冗余要求下，该 CDU 组合是否满足散热与接口要求？”任务需收集对应型号/版本规范、服务器或冷板条件、流量/压降资料，保存表格定位，复算边界，并列出缺失条件。交付是接口与计算表、适用范围和有保留的答案；仅找到三份 CDU 宣传册不能关闭此问题。上游制造及价格问题另有 question_id，但引用同一 CDU 对象。

## 6. 证据体系：既能存数字，也能存原理、约束和反例

保留当前 fact 的“一个指标×口径×时点×出处的数”，不要把它改造成什么都往里塞的万能字段。[fact 原子定义](/Users/m5/code/inresearch.ai/data/schema/fact.schema.json:3) 在旁边增加有类型的陈述/主张：定义、规范要求、结构关系、机制解释、事件、测试结论、预测和假设；它们都必须有范围与证据。否则低数字密度的标准、故障案例和工程原理会被体系性低估。

完整链条建议为：

`文件 hash → 文档版本/来源 → 原文片段或表格单元 → 提取候选 → 已采纳 observation/fact/statement → 计算或论证 → Finding → question answer → 交付物版本`。

支持和反驳均是有证据的边；计算值必须记录公式、输入 ID 和口径变换。来源保留 publication_date、数据 observation_date、预测 target_date、retrieved_at、reviewed_at；预测目标年很远不代表材料仍然新鲜。已有 originator 与 source_id 分离的原则应保留并扩展为“原始数据来源族”，十篇转述同一研究只算一个来源族。[originator](/Users/m5/code/inresearch.ai/data/schema/fact.schema.json:99)

“作者声称 X”与“X 已被证实”是不同的陈述。厂商规格可作为某版厂商承诺被采纳，不自动成为所有条件下的实测性能；一家机构预测可以准确提取并入预测表，不成为当前行业事实。

采用门槛按问题类型制定：

| 问题类型 | 可接受证据与验证 | 不能作出的升级 |
|---|---|---|
| 定义、版本规范、合同披露内容 | 可追溯的权威原文、明确版本与适用范围，关键条款/值核对 | 因有官方文件就断言实际履约或所有环境达标 |
| 工程性能、可靠性 | 测试配置/方法/负载/样本/误差清楚，关键计算可复算；高影响结论优先独立复测或比较 | 用标称最大值代替生产环境表现 |
| 价格、交期、供应与运营事实 | 时间、地区、规格、交易/报价类型与样本边界；必要时多个独立交易/资料族验证 | 用单笔报价当行业均价，用交付承诺当实际交付 |
| 行业分布、竞争格局与因果结论 | 总体与样本框、多个独立证据族、反例检索、竞争解释；说明剩余未知 | 多篇同源转载当交叉验证，把相关性直接写成因果 |
| 预测、情景与推算 | 已采纳输入、显式假设、可复算模型、敏感性、期限与事后评分 | 把预测值与已发生数据混合累计，预测自证预测 |

旧 schema 把所有“待交叉验证”的数一律禁止参与任何推算，这能防止误用，但也会阻断某份规范、单笔合同或模型假设的合理使用。[旧交叉验证定义](/Users/m5/code/inresearch.ai/data/schema/fact.schema.json:158) 建议改成上述按主张类型的规则：公共确定性结论严格把关；探索计算可以使用清楚标注且可替换的假设，输出必须保持“情景/试算”身份。不能用“放开规则”把未经核对的抽取直接放进核心事实。

## 7. 覆盖率：看哪些问题已经有可信答案

先冻结每轮研究的 scope_version：包括哪些对象、哪些场景、哪些必答问题、哪些问题关键。没有这个分母，“全面覆盖 80%”没有意义；也不能靠增加容易回答的问题把比例冲高。

建议分别展示五组状态，不合并成一个总分：

- **框架覆盖**：已定义问题与适用性的节点 / 当前范围内节点；仅证明研究有计划。
- **阅读履约**：已完成深读的唯一文档 / 当前批次应深读的唯一文档；另列无法读取、重复版本、超范围和等待修复，不能把失败算已读。
- **答案覆盖**：有明确回答、范围与证据链的问题 / 适用必答问题；暂定与验证通过分列。
- **验证覆盖**：通过该类问题门槛且未过期的问题 / 适用必答问题；关键问题单列数量和名单。
- **交付可复现度**：第三方能沿证据重建的关键结论/计算 / 本次交付全部关键结论/计算；同步显示未解决反证与口径冲突。

单个 question 可用状态：未定义 → 已定义 → 取证中 → 暂定回答 → 验证通过；另有争议中、过期、范围外。范围外必须给理由；“搜过但没有公开证据”可以关闭一项搜索任务并形成缺口报告，原研究问题仍是未知，不算已解决。已证明“现有公开资料无法分辨 A/B”可以成为新的有边界结论，但不能冒充 A 或 B 为真。

质量检查至少分列：可追溯、范围相容、方法充分、来源独立性符合要求、时间适用、反证已处理。一个高 importance 分数不能抵消无出处、错误分母或 OCR 未核。关键问题未通过时节点显示“关键缺口”，即便平均覆盖率很高；聚合比例只用于导航，同时展示各项分母和权重。

需要保留材料数用于调度，但从“资料充足→问题已答”的判断里移除它。现工单程序以材料数、高分数、是否有来源路径识别弹药与消化，且问题只要存在 `answered_by` 就跳过；新版必须验证答案范围、证据状态与新鲜度。[材料及路径计数](/Users/m5/code/inresearch.ai/pipeline/workorder.py:119) [answered_by 判定](/Users/m5/code/inresearch.ai/pipeline/workorder.py:321)

## 8. 双向工作循环与工单标准

### 8.1 Top-down：框架生成有验收标准的工作

链路为：目标能力/交付 → 场景与节点 → question → 证据缺口 → 任务包 → 信源路径 → 阅读与验证 → 答案/交付 → 更新缺口。

question 必须有稳定 ID，文本修改增加版本，不改变身份。workorder 也用稳定 ID 引用 question，不再把整段问题文本作为长期身份。当前四位摘要基于模块和文本内容，编辑问题可能换号；应迁移出文本身份，并保留旧 wid 兼容映射。[现工单号生成](/Users/m5/code/inresearch.ai/pipeline/workorder.py:153)

任务包至少含：对象与问题、地域/期间/型号/负载等范围、已有证据、缺少什么、执行类型、输入依赖、输出格式、验收检查、完成时限/预算、负责人、状态与失败出口。一次任务适合形成一个可独立复核的小交付，复杂行业问题用父任务拆分，不能给“把液冷研究透”这种无边界任务。

| 任务类型 | 合格交付 | 完成条件 |
|---|---|---|
| 找资料 | 与 question 对应的原始来源、命中页、检索记录及取不到的原因 | 来源确实相关且可回查；仅完成获取子任务 |
| 深读/提取 | 全文覆盖记录、逐节摘要、表图解释、候选事实/主张、问题与反例 | 原文覆盖、关键内容定位和异常登记满足阅读契约 |
| 口径整理 | 两套定义/分母/期间/配置对照、能否比较的判断 | 转换可复算；不可比原因明确；不能强行平均 |
| 独立核验 | 第二来源族或复测、支持/冲突说明 | 不是同源转载；不一致得到解释或转争议状态 |
| 建模/计算 | 输入引用、公式、假设、结果、敏感性和可运行材料 | 他人可复算；输出类型与不确定性正确 |
| 综合回答 | Finding、支持及反证链、范围、答案置信与下一验证点 | 匹配原问题、重要论断过门槛、未解决项明确 |
| 维护/复核 | 新旧变化、受影响下游、保留/修订/撤回理由 | 依赖答案与交付状态同步，不只改日期 |

优先级综合考虑关键依赖、实际决策影响、争议/过期风险、信息增益与成本；保留专门的探索和反方证据队列。不能把到期复核固定为低于搜新材料的 P3，也不能因为自主发现没有旧工单就自动降档。[旧复核优先级](/Users/m5/code/inresearch.ai/pipeline/workorder.py:315) [自主发现降档](/Users/m5/code/inresearch.ai/data/schema/submission.schema.json:11)

### 8.2 Bottom-up：每篇深读，产出不限于数字

遵守用户“每篇深读”：27B 第一遍粗读用于识别文件类型、语言、可读性、主题候选和队列优先级；第二遍对所有独立文章执行深读。低分只影响顺序，不取消深读。完全相同文件可复用同一阅读结果，修订版需做版本差异再决定重读范围；扫描损坏、密码保护等得到明确阻塞状态，不能标成完成。工程图纸、3D、数据集等先识别类型，采用相应的完整检查契约，不能当作短文章摘要。

“深读完成”应由过程与交付定义，不由模型参数量定义：覆盖全部正文、表图、附录与脚注；先逐节再全篇整合；记录关键定义与主张、方法与条件、表图解释、反例、局限与新问题；给出可定位的结构化阅读产物及页码覆盖日志。长文分块必须保留章节关系，不能只读标题和数字行。抽样 QA 用来检验读取质量，不能用抽样阅读冒充全文深读。27B 是否胜任特定语言、扫描质量和技术难度要用代表集测定，失败交给更合适的工具或复核者。

数字与表格先提取候选，再核对页图、表头、单位、脚注、负号、小数、倍率、合并单元格和行列位置。被采用的关键数逐项回原文核对；重要表格复算合计/比例并检查单位；OCR 与原页不一致保留两值和异常，不猜。能正确抽取不等于结论已获独立印证。历史已有造价表取错列与关键词误配的记录，这类检查应进入机器和复核契约。[造价列误读](/Users/m5/code/inresearch.ai/docs/DECISIONS.md:1437) [改名与关键词事故](/Users/m5/code/inresearch.ai/docs/DECISIONS.md:1536)

每篇深读的终态应是“已深读，全部候选有去向”：已采纳为事实/陈述；支持/反驳已有问题；只作原理背景；发现新问题；有争议待核；超出当前范围但已读归档；没有新的研究贡献。**没有新 Finding 也能成功完成深读，不能为了消化率硬凑结论。** 阅读完成、提取核验、研究采用三个状态独立保存。

旧标准的“高分消化”和仅 importance≥6 的半自动队列需修订；“精读即可直接引用”也应拆为阅读完成与证据采用；付费/独占数字、每页数字密度与跨模块加分不应压低原理、标准和失败案例。[旧阅读流程](/Users/m5/code/inresearch.ai/framework/04_reading_scoring_standard.md:5) [评分维度](/Users/m5/code/inresearch.ai/framework/04_reading_scoring_standard.md:19) [引用与队列规则](/Users/m5/code/inresearch.ai/framework/04_reading_scoring_standard.md:54)

## 9. 目录与 taxonomy 治理：允许学习，避免越读越乱

原始文件采用稳定对象/哈希身份，保留原名、来源和版本；规范显示标题与标签可改，文件身份不变。实体、物理层、问题、机构、年代、格式是不同筛选维度，目录只是可再生视图。多主题文章只存一份，可在多个节点出现；新增别名或研究问题不应触发物理文件搬家。

自动化可在现有登记表内提出/应用确定的标签、规范显示名和已有分类映射，但需记录规则版本、置信与前后差异。分数是动态元数据，不宜继续放入会驱动物理路径变化的文件名。实际批量搬移只根据已核对 manifest 执行：源/目标哈希对应、路径冲突检查、失败可重试与回滚、引用更新、目标内容核验；处理和阅读过程不临时决定搬家。旧记录曾出现 51 次改名回滚，说明显示名称与文件身份应分离。[旧命名规则](/Users/m5/code/inresearch.ai/framework/04_reading_scoring_standard.md:78) [历史改名回滚](/Users/m5/code/inresearch.ai/docs/DECISIONS.md:1536)

bottom-up 新发现依次尝试：

1. 已有术语的别名、产品版本或实例 → 关联现有节点。
2. 已有节点的新条件、参数、证据或新问题 → 更新对应登记，不新建大目录。
3. 稳定、可定义、具有独立关系或接口的子类型 → 提出新节点草案，写清与近邻区别、已有证据、用途和父/关联关系。
4. 跨越多个现有分类的新研究视角 → 先作专题视图和问题集合，待证明长期有用再调整主体系。

框架变更记录应含：提议及理由、定义与范围、关联材料/问题、备选映射、受影响对象与任务、旧新 ID 迁移、版本与生效日。结果为接受、合并为别名、暂缓或拒绝，均留理由。模型可以提交草案；小范围标签修正按已定规则运行；影响分类边界和已有答案的改动进入框架复核队列，不能由每篇读物触发无审查建目录。

重要的新术语即使暂未找到第二篇文献，也可以保留为“候选概念”并派验证任务；不必因证据稀少让新技术永远没有位置。但单篇营销材料不能直接重塑整套行业骨架。框架不是永久冻结，也不是跟每个标题摆动，而是小步、有来源、有迁移记录地演化。

## 10. 建设与长期学习节奏

### 导入前：把契约与代表样例做通

- 确定研究范围、对象/关系词表、R 视角、节点契约和证据门槛的 v0；标出待讨论边界，不宣称已经穷尽行业。
- 将 15 个旧模块和 116 条问题逐条映射到新问题/对象；每条说明保留、拆分、合并或退出及理由。拆分保留 parent_question_id，合并保留全部 legacy IDs。
- 对现有 BOM、facts、Finding、sources 做身份与引用迁移清单。验收是旧 ID 全部有去向，既有路径/哈希可回查、没有静默丢弃和重复计数；不能用“新列表更漂亮”代替迁移验收。
- 选三条贯通样例：供电→机柜→散热；工作负载→软件调度→计算/内存/网络；资产/合同→服务→现金流。每条至少包含旧资料、新资料、低优先级材料与有 OCR 问题的材料，检验全链路而非只用最干净样例。
- 验收一个真正闭环：从 3D/节点提出问题，找到原页、采纳候选、复算、生成有范围的回答，反证到来可使下游答案转复核。明确显示“未知”也属于成功的系统行为。

### 未来 4–6 周：形成能持续工作的研究节奏

第 1–2 周以代表样例验证读取质量和证据契约，完成关键对象骨架与全量旧问题映射；第 3–4 周扩大到主要系统和生命周期，建立原理/标准/实测/失败案例的平衡阅读队列；第 5–6 周至少完成一个可复核的端到端研究案例和一次框架修订回放。时间为建议目标，实际文档吞吐必须以代表集测量，不凭 GPU 或参数量承诺每日篇数。

验收看：每个核心系统有清楚定义、接口与关键未知；本轮关键问题均有答案或明确不足；所有被采用的数字与关键陈述可以回到原文；模型无法可靠读取的文件有修复路线；旧资料与新资料都能完成相同工作循环；一批低优先级文章也实际完成深读，证明“全部阅读”没有被优先级规则偷换。

### 3–12 个月：从资料系统变成可检验的专家能力

- **每周**：选择一个系统做不依赖摘要的讲解与推导，再回原始资料纠错；审阅重要冲突、失效案例和本周新问题；维护到期队列与读取积压年龄。
- **每月**：完成一个端到端比较或案例复盘，至少一次独立复算/条件检验；检查哪些结论因新证据发生修订，哪些只是材料增加；对薄弱视角补课，而非只追热点。
- **每季度**：冻结研究快照，做跨系统审查、框架边界复盘和预测回测；检查先前 12–18 月领先假设等是否有足够历史与定义一致的数据；没有样本就继续列为假设。输出“已知、争议、未知、最近改变”四项清单。
- **持续积累**：原理教材式节点档案、接口与架构图、证据化供应链图、范围明确的事实序列、可复算模型、失败案例集、标准/政策版本表、历史预测与修订记录。市场简报、公司分析和投资判断由这些资产生成，而不是反过来决定所有阅读价值。

长期衡量包括：能否解释陌生配置的工作方式与约束；能否在新场景正确迁移原理且说清限制；别人能否复算关键结论；实际错误能否被发现并追到下游；预测是否经过期限后的评分；重要未知是否持续减少。真正的行业专家系统必须允许自己被新证据纠正。

| 一律两个来源才可用于任何计算 | 按主张类型判断证据；单源规范/合同明确边界，假设计算保持情景身份，行业普遍结论严审独立性 |
| 材料数/高分数、Finding 数表示知识覆盖 | 以范围冻结的节点×问题、证据门槛、关键缺口和复现结果计量 |
| 文件名/目录位置承载材料身份与研究分类 | 哈希/文献版本/稳定 ID 承载身份，多目录为视图，变更有 manifest 和历史 |
| BOM 层级等于完整行业结构 | 装配、功能流、制造、产权、服务与地域是不同关系与视图，3D 承载其中的物理投影 |

这些是设计建议，后续实现需同步更新相关声明、schema、队列与输出，不能只改一篇框架文档让程序继续按旧规则运行。
