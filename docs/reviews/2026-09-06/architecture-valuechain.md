# 两套研究框架的边界校正与轻量关联模型

2026-09-06，设计评审；未修改仓库、迁移数据或部署服务。本稿依据主代理转述的两份附件结构，未把未提供的图中细节当作已观察事实。以下为建议，不自动替换现有模块与编号。

## 1. 主结论

两张图可以成为同一研究系统的两个观察入口，但不能拼成“企业只能落一格”的单棵树。应分清四种关系：物理组成、业务活动、资产权责、经济交易，再通过工作负载把数据中心能力与模型/应用需求连接起来。

“穷尽且互斥”的合理落点是**给定统计口径下、一条可分辨业务活动或合同交付项的主分类**，不是整家公司。混合交付无法拆分时应登记“组合/未拆分”，不能为了互斥编造收入分摊。企业可以跨层，场地和服务器也可以由不同主体持有、运营、使用和付费。

## 2. 两个原始资料场景检验

**场景A：买服务器并不等于拥有机房。** NVIDIA 的 DGX SuperPOD H100参考架构明确：客户可以拥有及管理硬件，部署在自有数据中心，也可以放在商业托管机房。同一架构同时列出计算、存储、计算/存储/管理网络及软件。这支持把设备资产、部署场地、运营方与软件栈分开登记，而非把设备客户一律归为“自建数据中心运营商”。这是2023年发布的具体架构例子，引用它来检验分类，不宣称它是最新产品配置。[NVIDIA参考架构：关键组件及部署](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-h100/latest/dgx-superpod-components.html)、[软件栈](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-h100/latest/dgx-software.html)

**场景B：同一公司既使用基础设施，也提供云与开发软件。** CoreWeave的2025年10-K披露：现有机房采用租赁、部分设备亦租赁；其平台交付包括基础设施、托管软件和应用软件服务，并支持训练与推理。推论是：一个公司记录需要多个按业务对象限定的角色；拥有产权不是供应算力服务的必要条件，租赁使用权、调度控制与对外销售服务应分别表达。[CoreWeave 2025 Form 10-K，Business及Leases](https://www.sec.gov/Archives/edgar/data/1769628/000176962826000104/crwv-20251231.htm)

这两例不要求增加一个新“行业”，而是说明企业/设备/场地/服务不宜共用同一归属字段。

## 3. 数据中心三层框架：保留主干，修正分界

| 附件层 | 可保留的核心 | 建议修正 |
|---|---|---|
| L1 运营/资源 | 场地、电力接入、机房空间、托管条件 | 内部至少分“资源与设施供给”“建设交付”“持续设施运营”。EPC是建设服务，不是资产运营；土地/电力是投入，不一定由机房运营者拥有。 |
| L2 硬件 | 计算、存储、网络、机电产品 | 这是产品/供给与物理系统视角。产品生产销售、安装集成、部署后持有是不同活动；不能把一台UPS同时作为硬件市场收入和机房资本开支相加成市场规模。 |
| L3 算力资产 | 服务器/集群资产及利用方式 | 建议称“计算资产与运营”，并显式区分法律产权、经济权益/租赁使用权、技术运营/调度、消费方、付费方和销售方。自用、出租、二手处置是生命周期/交易模式，不是永久企业类别。 |

具体边界：

- **产权、运营、支付、售出分别记。** 房东持有楼宇；另一主体持有或租用服务器；第三方代运营；模型企业使用；合同付款人可能是集团或渠道。未知的一项留空，不能从另一项推断。
- **电气与制冷按对象而非公司归层。** 设备型号/生产销售归产品视图；实际变电站、CDU、冷却塔部署归设施实例；供电合同、能源账单、运维服务归交易/运营视图。园区与机柜分界可作为导航，但共享管网、配电与制冷不能硬塞进唯一父机柜。
- **软件必须有位置。** 固件/驱动/通信库/集群调度/虚拟化/存储系统/监控影响“机器→可用算力”。它们是系统功能依赖和可能收费的产品/服务，不是把所有软件推到LLM工具层就算覆盖。
- **电信不可只表现为交换机。** 园区内计算、存储、管理网络，与园区间/互联网接入、专线、骨干、光纤资源、带宽收费分开。前者在BOM，后者有设施资源与服务关系。
- **上游芯片制造不可漏，但无需每层画进机柜爆炸图。** 芯片设计/IP、EDA、晶圆制造、先进封装、HBM/DRAM、基板、半导体设备材料，通过供应商/产品依赖链接；它们进入服务器供给约束和成本研究，不重复作为部署中的完整硬件数量。
- **资本、融资与政策跨层。** 资产融资、机房REIT/项目融资、GPU租赁、模型融资、预付款不是只属于某层的附注。资金来源、承诺额、支出、收入、贷款余额保持各自口径。

## 4. LLM四层框架：需要一个明确的工作负载连接点

- **L1生产要素不是同质串联产业层。** 算力、数据、人才、资本是跨阶段投入；训练和推理都需要算力，数据还涉及采集、许可、清洗、合成、评估、更新。把算力指向数据中心框架的计算服务/部署记录，不能复制一份GPU资产再计一次。
- **L2模型区分模型版本与提供者。** 架构/权重/训练配方/模型版本是研究对象，实验室与API提供商是企业角色。训练、后训练、蒸馏、评测、模型发布是不同活动；开放权重也会经第三方部署，不能假设模型作者就是推理服务销售方。
- **L3应拆出“部署运行”和“开发/分发工具”。** 推理引擎、托管/弹性伸缩、路由、缓存、计量是运行；评测、可观测性、开发框架、数据工具是开发支持；API聚合/渠道/Token销售是交易与分发。均可在图上同层，但数据库不能只给一个“工具公司”标签。
- **L4必须包括需求经济学。** 区分用户、调用者、付款客户、渠道与最终受益者；免费调用量、付费收入、付费保留率、可替代人工/软件成本、每次成功业务结果所需推理资源分别观察。自托管/端侧应用并不必经公开Token市场。

建议连接对象是 `workload`（工作负载），而非一根“应用→GPU需求”的箭头：

```text
应用场景/付费需求 → 请求及成功业务结果
                  ↓
模型版本 + 训练/后训练/推理类型 + 运行软件与服务约束
                  ↓
运行配置/部署集群 → GPU时间、内存、网络、存储、功率与能源
```

训练、推理不能用同一转换系数。推理还需区分prefill/decode、输入/输出、缓存、上下文长度、并发、时延目标、质量目标与重试；训练需要任务规模、并行方式、利用率和运行时间。**记账的GPU小时、实际运行GPU小时、有效完成工作量不能互换；API计费Token也不等于模型实际计算Token。** 能源从测量或有明确假设的场景计算产生，不能把合同电力MW当年耗电，更不能用应用收入反推官方未披露容量。

经济性研究使用两条可证伪桥梁：

1. 单位有用结果成本如何随模型、软件与部署变化；
2. 成本/售价变化如何影响付费采用与总工作量。

效率提升可能减少每次调用资源，也可能扩大调用量；净效果是研究问题，不预设“降价必然增加GPU需求”。

## 5. 计数与聚合必须先定边界

| 对象 | 正确的计数粒度 | 不能相加的例子 |
|---|---|---|
| 物理BOM | 指定配置版本、一个完整系统、选定部件层级 | 一套机柜+其中服务器+其中GPU作为三份同级设备资产 |
| 资产存量 | 指定地点、时间、状态下唯一资产或已披露资产组 | 产权方、租赁方和运营方各报一次后加总 |
| 产能/供给 | 指定状态与口径、去重后的设施/集群 | 同一项目公司口径与园区口径重复；预留/在建与投运混加 |
| 产品流量 | 期间出货或安装，明确新增/替换/转售 | 累计出货直接当现役库存，二手再次成交当新增算力 |
| 交易金额 | 合同交付项、交易阶段、期间、币种、总额/净额 | 服务器销售额+云服务收入+模型API收入+应用收入称为“总AI需求” |
| 使用量 | 指定工作负载/模型/硬件/SLA的测量 | GPU型号、精度、模型与延迟条件不一致而比较token/s或GPU小时 |

BOM描述“由什么组成”，供应链描述“谁供给什么”，交易描述“谁为何付钱”，资产表描述“何时何地谁控制什么”。四种图可以共享ID，不能共享加总规则。

## 6. 轻量关联数据模型（复用现有JSON，查询可派生SQLite）

不需要图数据库，也不把Spark原件库塞入Git。先保留现有 companies/projects/products/bom/sources/facts/findings，补稳定ID与几组有类型的关联；按需要增量建表，不一次性建完整资产管理系统。

| 对象 | 最小主键及关键字段 | 与现有内容的关系 |
|---|---|---|
| 企业/法律实体 | company_id，parent_id可选、别名、地域 | 复用companies；集团和子公司关系显式，避免交易主体混淆 |
| 功能部件 | bom_part_id，功能分类、允许组成关系 | 复用bom.parts；代表“GPU/存储/冷却”等类型，不代表某台实物 |
| 产品/服务/模型版本 | offering_id，kind，提供方、型号/版本、规格证据 | 产品目录补稳定product_id；软件、云服务、模型用kind区分，不冒充物理部件 |
| 设施与部署组 | site_id/instance_id，parent、地点、型号/配置、数量、状态、as_of | 复用projects；已披露时再加集群/资产组，不要求逐台序列号，未知数量留null |
| 参与角色 | assignment_id，company_id，role，object_ref，范围、有效期、evidence_refs | owner/lessee/operator/host/provider/customer/payer/integrator/lender分别记录；角色必须指向对象 |
| 合同/交付项 | contract_id/item_id，买卖双方、交付对象、类型、单位、期间、定价/支付结构 | 扩展contracts；自用不伪造外部交易，组合合同未拆分不猜分摊 |
| 工作负载 | workload_id，类型、model_version、deployment_ref、运行配置、需求/SLA、测量事实引用 | 连接设施能力、模型与应用；仅记录观测或标明假设的情景 |
| 问题与结论 | question_id/finding_id，问题、所属研究模块、覆盖对象、状态、反证条件 | 复用研究模块与Finding；重构导航时保留旧ID与映射，不丢历史证据链 |
| 文档与版本 | doc_id/doc_version_id，sha256、来源、版本、权限、Spark解析地址 | Spark保存原件/完整台账；Git sources发布所需元数据，doc_id不依赖文件名/目录 |
| 证据与事实 | evidence_id，doc_version_id、定位、片段哈希；fact_id，subject_ref、metric、value/range、unit、caliber、as_of、evidence_refs、采用状态 | 复用facts；区分“提到”“支持”“反驳”，模型阅读结果先成为候选 |

关联可使用短JSON表，关系词限定词表并校验两端类型。例如 `product_realizes_part`、`instance_of_product`、`deployed_at`、`operates`、`owned_by`、`uses_service`、`supports_claim`、`answers_question`。不要任意自然语言边替代可校验字段。BOM组成关系、企业业务参与和交易各有自己的表，不用单一parent字段模拟所有关系。

**一条完整但不编造数值的样例链：**

```text
问题：某类推理服务的成本下降来自哪里？
→ workload W（模型版本、时延约束、prefill/decode配置）
→ deployment D（某设施上的服务器组，数量未知则留空）
→ 产品型号 P → bom_part gpu / network / storage
→ 角色记录：企业A运营D、企业B提供场地、企业C购买服务
→ facts（测得GPU时间、价格、功率、吞吐，各有单位/时间/口径）
→ evidence（原文页码或单元格）
→ doc_version（SHA-256）→ Spark原件解析入口
```

该链能让用户从物理爆炸图进入产品/企业，再到相关问题与证据；也能从一条Finding倒查事实、资料和具体部署。沒有资料支持的中间环节明确缺失，不能由模型补齐成漂亮闭环。

## 7. 实施前最少要锁定的契约

1. 编号分命名空间：数据中心视角与LLM视角不能都用裸L1；九级项目状态L1–L9、现有3D下钻层级另保留。可用DC1–DC3、AI1–AI4作展示代号，名称是否采用由总设计决定。
2. 企业ID不随分类改变；业务角色带对象、时间和证据。未披露不根据品牌名/租赁模式推断产权。
3. 文档身份、证据身份、事实身份分离；改名/移动原件不改变引用，源文件版本变化不覆盖旧引用。
4. 所有聚合声明计数粒度、去重键、单位、日期和包含状态；BOM图展示不能自行生成市场规模或供给总量。
5. 采用的知识与Spark读取结果只有一条批准/校验路径；Spark不因读完文件自动改成current Finding。
6. 先拿一个真实托管集群场景、一条模型推理服务和一篇多模块资料做贯穿样例，再扩全库；不要求先重建全部15模块或上新数据库。
