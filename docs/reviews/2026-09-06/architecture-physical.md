# 数据中心物理研究架构专题建议

日期：2026-09-06。范围：只读审核现有物理 BOM、3D、产品与证据契约，并提出导入资料之前应确定的架构。本轮没有修改产品源码或数据，没有操作生产服务。用户给出的 DC 三层、LLM 四层框架已阅读；本文聚焦物理实体、系统关系、3D 和逐层资料研究。

## 1. 核心结论

应保留“从园区不断深入到服务器内部”的体验，但不能把“园区→楼宇→系统→机柜→部件”强制存成一棵唯一父子树。园区、楼宇、机房是空间；供电、散热、网络是跨空间运行的系统；机柜、服务器、板卡是装配对象。一个 CDU 服务多个机柜，冷板冷却 GPU，冷板和 GPU 却不因此互为装配父子。

建议以“空间包含树 + 物理装配树 + 带类型的系统关系图”为共同底座。3D、BOM、产品库、研究材料、任务和产业链都是这个底座的视图。实体身份、厂商型号和现场实例需要分别建模；几何细节与事实可靠程度也需要分别表达。

穷尽且互斥应当定义为：在明确的研究边界、设施基型、配置版本和拆分终点内，每个实际对象有唯一身份及可解释的归属，每个必需位置要么有对象，要么明确“不适用/未知/待确认”。不要宣称一个通用静态分类能够穷尽所有历史和未来数据中心。

## 2. 目前真正已有的能力和契约

### 2.1 目前 BOM 是 46 个研究类别，尚不是物理组成模型

实际文件是 [framework/bom.json](/Users/m5/code/inresearch.ai/framework/bom.json:37)，并不存在作为当前 BOM 主源的 data/bom.json。当前五层如下：

| 现有层 | 数量 | 当前节点 ID |
|---|---:|---|
| L1 园区 | 9 | grid, substation, prime-power, backup-power, bess, water, land, network-access, fuel-supply |
| L2 建筑 | 2 | shell, fire |
| L3 机房 | 10 | ups, power-dist, room-cooling, cdu, heat-reject, dcim, cabling, immersion, leak-detection, modular-dc |
| L4 机柜 | 9 | rack-frame, server, network-switch, manifold, power-shelf, storage-array, copper-interconnect, coolant, sidecar-hx |
| L5 部件 | 16 | gpu, cpu, hbm, nic, optics, coldplate, psu, fpga, interconnect-chip, dram, ssd, hdd, switch-asic, fan-vc, vrm, connector |

每条记录基本字段为 id、layer、name、module、companies、series、indicators、status、desc。可以从部件类别进入研究模块、公司、指标和产品目录。这是已有的有效研究索引，适合作为迁移时保留的旧 ID 锚点。

它缺少 parent_id、组成关系、配置版本、实际站点/设备实例、数量、端口、具体产品型号引用，以及“哪份资料哪一页证明这个节点/关系”的契约。现有 layer 不能回答某个机柜里装了哪台服务器，也不能回答哪个 CDU 连接哪条回水管。

现有分类还混合了几种不同对象：

- land 包含资源/权利语义，grid 是可能处于园区边界外的基础设施；dcim 包含软件；immersion 是技术路线；modular-dc 是设施形态。
- fire 同时覆盖消防与安防；power-dist 同时覆盖母线/PDU/配电柜；manifold 包含快接；power-shelf 包含 BBU；fan-vc 包含风扇、均热板与散热器。这些都应拆为具体物理类型，再用系统/主题聚合。
- hbm 与 dram 已有两个类别，但 hbm 的宽泛命名仍需收紧。现有 GPU upstream 的晶圆代工、先进封装工艺和供应商，不都属于 GPU 的物理子件，应分别归入制造过程、供应关系、封装实际组成。

## 3. 建议实体和关系模型

### 3.1 分开类别、型号与实际对象

建议至少定义下面这些概念；这是概念契约，不要求立即引入图数据库或 BIM 引擎。

| 概念 | 示例 | 唯一身份及用途 |
|---|---|---|
| component_type | 冷板、HBM 堆栈、计算托盘 | 稳定分类与研究问题模板 |
| product_variant | 某厂商某型号某硬件 revision | 结构化规格、参考装配、适用文档 |
| space | 某园区的 A 栋 2 楼机房 | 真实空间边界和空间包含 |
| asset_instance | 某机柜内某台具体服务器 | 安装位置、序列号/资产号、生命周期、现场配置 |
| system_instance | 某机房的 TCS-A 液冷回路 | 实际成员、端口连接、流向、运行参数 |
| configuration | 某时点的设施/设备配置 | 避免扩容、换件、设计图与竣工图互相覆盖 |
| material | 某版图纸、规格书、记录文件 | 文件身份、hash、版本、来源、权限 |
| assertion + evidence | “该服务器安装在 R01”及其依据 | 节点属性和关系的可核实断言 |
| research_task | 确认 R01 使用的冷板版本 | 指向对象/断言、要求材料和验收条件 |
| geometry_representation | 某节点的一套 GLB/CAD/简化形体 | 语义映射、单位、版本、许可、真实性级别 |

产品型号的“标配 8 块 GPU”与某台现场设备“实际安装 8 块 GPU”是不同断言。前者不能自动填成后者。参考装配也不能悄悄成为真实园区资产清单。

### 3.2 空间树与装配树负责不同问题

空间主线：园区 → 建筑 → 楼层（可选）→ 房间/机房/明确服务空间。室外变电设施、冷却设施可直接 located_in 园区分区；预制舱可以作为一种可定位的空间容器。排/列/Pod 有时是区域，有时只是运维分组，要记录其种类，不能把逻辑分组当作另一个重叠物理空间。

装配主线：机柜 → 装入的设备 → 托盘/机箱子装配 → 板卡/载板 → 模块/封装 → 包内物理子件。不是每一型号都经过所有层，也不是机柜才可以作为设备父对象。机房 UPS、冷水机、储罐都可以从其自身装配继续下钻。

一个装配子件在同一配置中最多有一个直接装配父对象；整个装配的空间位置向下继承，避免把螺丝、GPU、HBM 都同时直接登记到机房。IFC 对空间包含与装配聚合也有明确区分，可以借用其语义而无需本轮实施完整 IFC。[buildingSMART 空间包含与装配](https://standards.buildingsmart.org/IFC/RELEASE/IFC4_3/HTML/concepts/Object_Connectivity/Spatial_Structure/Spatial_Containment/content.html)

### 3.3 关系类型必须可区分

| 关系 | 含义 | 规则/典型例子 |
|---|---|---|
| part_of | 物理装配归属 | GPU 封装属于加速器模块；同配置唯一直接父对象，无环 |
| located_in | 安装/空间位置 | 机柜位于机房；与所有者分开 |
| member_of_system | 系统参与关系 | CDU 参与液冷系统；不改变其物理归属 |
| port_connected_to | 端口实际连接 | 指定端口、介质/协议、额定参数；物理连通本身不必带单向语义 |
| supplies_power_to | 电能供应关系 | UPS → 配电路径 → 机柜；A/B 电源分别识别 |
| coolant_flows_to | 冷却液流动 | 供液、回液分开；标识流体与回路，不能穿过换热器默认混液 |
| transfers_heat_to / cools | 热传递/冷却对象 | GPU 经界面到冷板；冷板冷却 GPU 不意味着 GPU 是冷板的子件 |
| carries_data_to | 数据通路 | 根据网络层/平面定义；可双向，不与电力线混为一种 generic link |
| monitors / controls | 监测与控制关系 | 漏液传感器监测回路；DCIM 软件运行在设备并读取系统 |
| manufactured_by / owned_by / operated_by | 制造/所有/运营角色 | 不用公司作为物理包含父节点 |
| deployed_on / consumes_capacity_from | 软件及工作负载使用 | LLM 部署或作业使用集群；模型不是 GPU 的物理子件 |

CDU 一侧接设施水，一侧接技术冷却回路；冷板、机柜歧管、软管、快接、CDU 的安装/质保材料需要保持同一实际回路的适用性。OCP 的 TCS 集成资料和设施参考设计提供了这种跨设备关系的依据。[OCP 液冷集成与物流](https://www.opencompute.org/documents/ocp-liquid-cooling-integration-and-logistics-white-paper-revision-1-0-1-pdf)、[OCP 设施参考设计](https://www.opencompute.org/documents/ocp-acf-reference-design-guidance-white-paper-r1-pdf)

### 3.4 “系统视图”如何进入连续下钻体验

用户可以走“园区 → A 栋 → 机房 → 冷却系统 → CDU → 泵/换热器”，也可以走“园区 → A 栋 → 机房 → R01 → 服务器 → 冷板”。界面保留这两条探索路径，但前一条经过“系统成员”关系，后一条主要经过空间和装配关系。面包屑要标记关系类型，不能把一次导航路径反写成新的所有权树。

选中冷板时，右侧同步给出：它属于哪套服务器冷却装配、冷却哪些封装、供回液接哪两个端口、材料和哪些任务尚未完成。用户不必理解图数据库，也能看到实物、功能与研究证据是如何对应的。

不要继续用裸 L1/L2/L3 为新的物理深度命名：用户附件的 DC L1–L3、LLM L1–L4 和现有成熟度分级已有其他含义。存储使用明确 node_kind；显示可用“园区/建筑/机房/机柜/设备/装配/部件/封装内部”等名称。

## 4. 如何实现“穷尽且互斥”

先固定研究对象边界、设施基型、配置时点、拆分终点。对于每个父对象，模板明确“必需/可选/条件必需/不适用/未知”的子件位置、数量口径及证据要求。实际清单按唯一实例 ID 排重，研究类别按物理定义归类，多系统参与用关系表达。

应有如下完整性检查：

1. 同配置的空间包含树和装配树无环；装配对象无两个直接装配父对象。
2. 每个实际对象有类型、配置、位置来源或可追溯的父装配位置；别名不得制造第二个对象。
3. 每个必需位置都有实际对象或明确缺口；未披露不能推定为不存在。
4. 多台相同型号设备可以有多个实例，但产品规格和文件共用同一型号记录。
5. 相邻设备端口的介质、电压/协议、尺寸与连接方向不能相互矛盾；缺参数时先标未知。
6. “园区自有设备”和外部电网/市政水/运营商网络的分界点明确。电力配额、水权、PPA、租赁合同是事实或权利，不制造成伪设备。
7. 上游制造工艺、供应商和最终物理子件分开；CoWoS 是工艺/封装技术标签，不是一个能直接当作实装器件的子件。
8. 研究拆分终点有理由：可更换件、可单独采购件、影响性能/供需/成本的关键部件，或已经到证据边界。普通紧固件可集合化；关键稀缺件不可随意合并。

以下是覆盖面核对清单，不应直接复制成又一棵把功能与实体混合的树：

| 物理范围 | 应覆盖的对象类别与接口 |
|---|---|
| 园区与建筑 | 边界、场坪道路、装卸与维护通道、室外设备区；基础、结构、外墙屋面、分隔/防火分区、竖向交通；机房、配电/电池/机械/网络接入等空间 |
| 供配电 | 电网交接、开关设备、变压器、UPS、发电机、燃料设备、BESS、蓄电池/BBU、母线、PDU、机柜电源层、PSU、VRM、线缆连接器；保护计量、接地防雷 |
| 冷却与流体 | 冷水机/干冷器/冷却塔等排热设备；泵、换热器、CDU、歧管、管路、阀门、过滤/水处理、软管快接、冷却液；冷板/TIM、CRAH/CRAC、风墙、机内风扇/散热器、后门换热器、浸没槽 |
| 网络与互连 | 接入机房/边界设备、管理/业务/存储/加速器互联平面；交换机、NIC/DPU、光模块、线缆/连接器、配线组件；逻辑网络与物理连接分别保存 |
| 计算和存储装配 | 机柜/导轨、机箱/托盘、主板/背板/载板、CPU、DIMM、加速器模块/封装、HBM、交换 ASIC、BMC、SSD/HDD、控制器、电源与散热子装配 |
| 消防、安防和监控 | 消防检测/灭火设备、门禁/摄像设备、漏液与环境传感器、控制器；同一设备被多个系统引用时不重复建实体 |
| 外部接口和非物理配套 | 外部电网/供水/网络端点；土地/电力/水/许可/合同；操作系统、固件、调度、DCIM/BMS 软件版本与部署关系 |

供配电、冷却等表项是覆盖维度；最终物理对象只创建一次。例如机内风扇属于服务器装配，也参与散热系统；其存在不需要在两套资产树各复制一次。

## 5. 设施基型：模板应可以组合，不能只有一种万能机房

建议基型由几个正交维度组合：空间形态、计算/网络装配、冷却拓扑、供电拓扑和部署阶段。运营商/托管/自持出租属于商业角色，不应当成为物理基型的替代。

| 基型/变体 | 组成与关系的实质差异 | 3D/材料重点 |
|---|---|---|
| 传统空气冷却通用计算/存储 | 机柜、通道组织、机房送回风和机内空气路径为主 | 机房布局、气流组织、机柜功率和设备进出风方向 |
| 高密度 GPU 服务器直接液冷 | 芯片冷板、TCS、CDU/设施侧排热；剩余器件可能继续风冷 | 冷板兼容性、供回液、机柜歧管、流体和泄漏/交付测试 |
| 机柜级紧耦合加速器系统 | 计算托盘、交换托盘、背板/线缆、电源层/母排等配置高度依型号 | 厂商参考装配、真实配置 revision、服务/替换边界；不可套用“8 托盘×8 GPU” |
| 浸没式 | 槽体、介电液、槽内装配/操作方式及外部换热路径改变 | 流体材料兼容性、槽体/维护搬运、实际散热与供电连接 |
| 既有机房液冷改造 | 原 FWS/空间/承重与新增 CDU、管路或后门换热器共存 | 改造前后配置、结构/配电余量、施工切换、维护空间 |
| 预制化/集装箱/边缘设施 | 空间容器与部分机电设备组合交付，未必有传统楼层/大厅 | 模块边界、运输安装、现场接口、独立维护与扩展 |
| 多层建筑/大型园区 | 立管、竖井、室外集中机电、多建筑共用设施 | 跨空间系统连接、共用与专用容量边界 |

OCP 分别提供机架、供电、BBU、歧管与相关接口资料，可以支持“按产品/配置选模板”；它们不是所有设施必须同时安装的通用清单。[OCP Open Rack 规格与设计](https://www.opencompute.org/wiki/Open_Rack/SpecsAndDesigns)

训练、推理、prefill/decode 等属于工作负载和需求模型。它们会对内存、网络、功率、散热提出约束，但不应作为园区或 GPU 的物理子节点。应通过 workload/service → consumes_capacity_from/deployed_on → 实际或规划资产关系接入。

## 6. 每一级都同步关联材料和研究任务

### 6.1 一个材料身份，多处精确引用

统一 material_id，并把已有 doc_id、source_id 作为可追溯旧标识。记录原文件 hash、来源 URL、本地文件、发布/采集时间、版本、许可/保密范围、有效/被替代状态。相同文件不要因为被五个节点引用而复制五份。

材料归档和证据引用分开：一份百页安装手册是一个 material；“第 42 页图 7 证明冷板端口方向”是一个 evidence。evidence 指向 node_id、relation_id 或 assertion_id，包含页/表/图/CAD 对象定位及适用型号、revision、配置时点。

必须区分以下结论：

- 已有文件，不等于已经读懂并抽取。
- 厂商规格已经证实，不等于某现场已安装这一型号。
- 设计图证实了规划，不等于竣工与当前运行状态。
- 型号通用材料可以向实例继承展示，但必须标为“型号参考”，不能充当现场安装证明。
- 文件新旧、采集时间、事实时点和设备配置版本分别记录。

### 6.2 节点页的固定阅读顺序

每一级采用相同结构：身份与真实性标记 → 在哪里/属于谁的装配 → 子对象及缺口 → 电/热/数据关系 → 核心规格和时点 → 原始材料及精确证据 → 已知结论/争议 → 下一步研究任务。

任务至少保存 task_id、node_ref/relationship_ref、configuration_ref、研究问题、需要的材料类型、待核实字段、验收条件、负责人、优先级、状态。验收应是“核对到某版资料某页并解决了哪个问题”，不能仅以“上传了一个 PDF”完成。

覆盖度建议分成四项：结构完整度、型号/规格核实度、现场安装核实度、运行数据覆盖度。每项允许未知和部分核实；不要把一份营销手册计作整个机柜的满覆盖，也不要沿用 tight/mature 市场状态表示证据质量。

## 7. 可实现的完整示范链：园区到冷板

下面是实施模板，不是对某个现有园区的已知事实。首个样板应选择能拿到足够资料的真实项目；拿不到的层级明确保留缺口，并提供分离的厂商参考装配。

空间链：真实园区 S → 建筑 B → 楼层 F（如适用）→ 机房 H。
定位关系：机柜 R located_in H。
装配链：R → 服务器/计算托盘 A → 其冷却子装配 C → 冷板 P。
旁支：A → 计算板/加速器模块 → GPU 封装 → HBM 堆栈（仅当该型号/封装资料支持）。
功能关系：P cools GPU；P 的供回液端口连接 TCS；GPU 和冷板不因散热关系互为装配父子。

实际厂商若把冷板作为别的 FRU/总成的一部分，就按其结构调整 C，不先验编造统一层级。短层级允许跳过，不能为了视觉连续性增造不存在的物理装配。

| 深入对象 | 最小材料包 | 需要先回答的问题 | 可接受的完成证据 |
|---|---|---|---|
| 园区 | 项目官方资料、总平/边界图、规划或竣工阶段说明、外部电/水/网络接口资料 | 是哪个实际地点、哪些建筑/设施属于本次边界、处于什么阶段？ | 可定位边界及建筑身份；容量口径与时点清楚 |
| 建筑/楼层 | 建筑平立剖、结构/承重、空间和消防分区资料，设计/竣工版本 | 哪层哪房、哪些路径能安装维护、哪些区域未披露？ | 空间标识与尺寸/版本相互一致；未知区域明确 |
| 机房 | 机柜布局、设备/配电清单、单线图、管路与仪表图 P&ID、布线/制冷设计 | 机柜位置、供电回路和冷却边界、哪些是实际/规划？ | 空间、设备清单、系统端点可以互相核对 |
| 机柜 R | 机柜立面/U 位表、实际资产清单、安装记录、机柜/电源/液冷接口手册 | 哪些设备真正装在 R、装多少、接哪路电和液？ | 现场配置 revision、数量、定位与端口证据；照片只能证明可见部分 |
| 服务器/托盘 A | 厂商型号/硬件 revision、安装和服务手册、FRU/装配信息、现场交付/资产记录 | 实装型号与参考设计是否一致、哪些板卡和散热总成可替换？ | 型号装配与现场身份两条证据均成立 |
| 冷却总成 C | 冷却装配图/BOM、接口和软管布置、适配列表、泄漏/压力/集成交付测试 | 冷板属于哪个总成、如何连接、与该服务器是否兼容？ | 精确 revision 和接口对应；连接关系有原文定位 |
| 冷板 P | 冷板规格/工程图、材料与流体兼容性、流量压降及热性能条件、质量验证资料 | 冷却哪些芯片、额定工作窗口、压降/热阻的测试条件是什么？ | 条件完整的性能事实、兼容性证据、明确供回液连接；未披露内部流道保持未知 |

这一链条的实际难点通常是“现场安装证据”和“具体装配 revision”，不在于渲染更多三角形。可先用明确来源的简化几何把链与证据跑通，再增加外形精度。

同一示范中可以显示三条独立系统路径：

- 电：设施配电路径 → 机柜供电 → 电源转换 → 板级 VRM → 芯片；每段按实际拓扑和端口核实。
- 热：芯片 → 热界面材料 → 冷板 → TCS → CDU 换热边界 → FWS → 排热设备。它是热传递路径；冷却液的供回循环另画，不表示两侧流体混合。
- 数据：设备端口 → 机柜/集群互联 → 上级网络；训练集群的不同网络平面分别呈现。

若需要一直深入 HBM：在有制造商依据的 GPU/加速器封装下展示封装基板/中介层、逻辑芯片及 HBM 堆栈的实际组成；堆栈内部层数、尺寸和位置要对应具体器件版本。只有一般封装论文时，显示为“封装原理示意”，不能作为该园区那块芯片的已验证结构。

## 8. 真实 3D 与概念 3D 的边界应成为数据字段

建议每套几何分别声明：

| 表示级别 | 含义 | 可以说什么 |
|---|---|---|
| actual_verified | 有明确对象、版本、尺寸/现场依据 | 对应某个真实对象；只对有依据的部分作此声明 |
| vendor_reference | 有来源的具体厂商型号参考几何 | 这是该型号参考；安装到某处需要另一条证据 |
| conceptual | 拓扑/原理或通用形态的说明 | 表达结构与关系；尺寸、数量可能为示意 |
| unknown_placeholder | 已知有对象或必需位置，形态未核实 | 显示存在/缺口，驱动补充资料 |

完整几何契约应包括 node/variant/configuration 引用、模型 hash、单位与坐标系、源比例或非比例声明、来源与许可、版本、mesh → semantic node 映射、可见/被简化范围、爆炸变换基准，以及该几何依据的材料定位。美术细节质量与事实状态两条轴并列。

即使外部楼宇可以按真实轮廓建模，也不能自动在内部填入虚构的精确机柜数和 GPU 数。可在已确认边界处进入“该型号参考装配”，用清楚的状态切换继续下钻，直到研究材料足以绑定现场实例。这样仍能交付从园区到芯片的连续研究体验，同时保持现场事实可验证。

## 9. 与用户两张研究框架的对齐

DC 三层划分的是运营/资源、硬件制造与分销、算力资产持有/变现的商业活动边界。物理设施和服务器资产可以同处一栋楼但由不同主体持有运营；例如 L1 的机房经营者给 L3 的服务器持有者托管，L2 的厂商供应机柜/部件。同一个物理对象使用唯一 ID，商业关系和公司研究独立引用它。

LLM 四层从生产要素、模型、使能流通到应用消费，适合通过需求、部署和使用关系连接到数据中心。训练/推理工作负载带来算力、内存、网络、能源需求；模型公司和算力持有者可以是不同主体。模型、Token 服务和应用不应塞入物理装配树；需求情景的估计值也不能冒充已安装容量。

用户图中的“实体一个归属、横切面贯穿、公司独立成库”可落实为：物理实例不重复创建、主活动分类有边界、多种系统/商业/需求关系允许引用同一实体。

## 10. 导入资料之前的实施顺序与验收

1. 定义边界和词汇：确定类型、实例、空间、系统、配置、材料、断言、任务、几何这十类对象的最小契约；明确所有关系的方向、基数和时点。先选择设施基型与一个实际样板，不要求所有类别一次填满。
2. 做架构样板：用有限且有出处的材料手工走通一条园区到冷板链、一条电力路径、一条散热路径、一条数据路径。此时重点是研究对象和资料契约，不进行全量导入。
3. 建立验收集：验证唯一归属、无环、引用存在、材料定位、型号和实例不混淆、配置版本独立、未知可见。使用 CDU 跨多个机柜、双路电源、共用建筑设施、部件替换作为边界案例。
4. 制作迁移映射：当前 46 类保留旧 ID/别名，拆分宽类别并记录映射；175 产品线接入 product_variant 层之前先规范型号；旧 source_id/doc_id 映射统一材料身份。研究模块仍可作为视图和派工组织，不承担物理身份。
5. 契约稳定后再导入：按节点与问题清单归档/抽取材料，先导入最能补齐实装身份和关系的数据。仅有市场资料的部分停留在类型/供应关系层，不伪造现场证据。
6. 最后升级 3D：从结构化对象和关系生成/绑定场景，点击选择唯一对象并显示其证据与任务；增加机柜内部细节或采购 CAD 模型前，先通过样板链验收。

建议首个架构里程碑的完成标准：一个真实园区及建筑身份已核实；一条内部空间/装配链的事实与缺口全部明确；每一级能打开至少一种对应材料或明确待补任务；系统关系不会被误写为父子归属；参考装配和实装对象在界面与数据上始终可区分。达到这一步之后，全量资料导入才会有稳定的归属和验收方式。
