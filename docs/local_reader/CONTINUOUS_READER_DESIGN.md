# Spark 持续资料处理系统：设计草案

2026-09-06。用户本轮先讨论方向；本稿记录明确要求与工程建议，尚未实施服务、迁移原件或修改现行阅读/采用代码。与旧版有限批处理协议冲突之处在末节列出，不能直接拿旧启动指令开跑。

## 1. 用户明确的目标

- 历史文章以前主要经过大模型粗读与排序；今后还会持续补充原始材料。
- Spark 持续接收 `raw materials` 中的文件，由 27B 先粗读，再对每篇文章深读，判断如何处理、改名、重新归类，并维护文件夹逻辑。
- 单轮可能持续十几天或三十多天，日常新增不会停止，因此按长期服务设计。
- 本轮先把思路考虑清楚，不等于已经要求启动全天候任务。

**每篇都应进入深读，粗读只改变顺序，不设置低分淘汰线。** 完全相同的原件可继承经核实的阅读成果并记录继承关系；不能凭标题相近认定重复。工程素材不是文章，须有相应的结构普查与处理结果，不能冒充“文章深读完成”。

## 2. 一篇材料如何经过系统

```text
传输完成 → 登记原件/版本 → 提取与页面检查 → 27B 粗读
                                               ↓
                                        排入完整深读队列
                                               ↓
                       按章节/页块深读 → 全文综合 → 质量检查
                                               ↓
                          自动命名归类 + 阅读报告 + 检索索引
                                               ↓
                              候选事实/结论 → 既有采用流程
```

各文件独立推进，新料不必等旧料全读完；也不等全部文件完成后才整理目录。一篇加密或解析失败只影响该篇。资料归档、读完和研究采用分别记账：

| 维度 | 示例状态 | 不能据此推断 |
|---|---|---|
| 接收 | 传输中、已登记、完整性异常 | 已登记不代表已读 |
| 阅读 | 待粗读、粗读完成、深读中、部分完成、深读完成、继承已读结果 | 有摘要不代表全文覆盖 |
| 质量 | 待检查、通过、需返工、部分无法核实 | 深读完成不代表每个数字已核实 |
| 整理 | 待归类、方案生成、已归档、需纠正 | 进入最终目录不代表已采用 |
| 采用 | 无新增存档、来源补充、事实候选、Finding候选、已采用、暂缓 | 登记 sources 不代表已消化 |

## 3. “深读”的可检查定义

27B 粗读识别标题、机构、日期、材料类型、目录、主题、阅读难度、初步价值和可能关联的研究问题。结果为暂定判断，粗读摘数不能直接变成已核实事实。

深读重新访问原文，不能仅对粗读摘要进行扩写：

1. 建立正文、附录、脚注和图表的覆盖清单。长文按章节及语义边界分块，记录每块页码与结果，再综合全文；所有实质内容都有处理记录后才满足覆盖门槛。
2. 提取作者主张、依据、方法、样本、假设、适用范围、反例和不确定性。覆盖率是必要条件，不足以证明理解正确；还需抽查论证和引用是否吻合原文。
3. 有意义的图表要识别行列/坐标、单位、时点、实际/预测标记和脚注。缺页、乱码或实质表格无法解释时标部分完成，并生成补读任务。
4. 原文阅读结束后，再查询已有研究，判断新增、补强、冲突、历史版本、信息重复或无可采用增量；保留所用研究快照，避免循环引用自己的旧摘要。
5. 输出处理结论与理由。每篇都有阅读成果，不要求每篇产生新 Finding，也不要求凑固定数量的事实。

当前 infra 的 `brain` 路由为 `qwen3.8:27b`，配置上下文上限 32,768；实际输入还须给指令和输出留空间。因此超长报告必须分块，分章结论过长时继续分层综合，不静默截断尾部。粗读和深读均明确指定 27B；失败转重试或异常，不能无记录降级成其他模型。

扫描页先由 OCR/视觉工具恢复内容，再交 27B 阅读；27B 能读提取文本不等于已经看懂原始图表。现机已有视觉模型，OCR 路线及准确率仍待样本验证，不能以安装了模型充当质量验收。

采用数字的证据至少包含原件哈希、文档ID、PDF页索引/印刷页码、章节/表号、原文片段，以及页面区域或工作表单元格地址。原生表格优先读取单元格、公式和表头结构；扫描表核对原图。单位、负号、小数点、区间、预测标记和跨页续表单独检查。识别一致、来源等级与独立信源交叉验证是三件事；两个模型读出同一个数不等于两个行业来源证明它。

## 4. 文件布局与整理规则（建议）

统一数据根目录：`/home/spark/.local/share/inresearch.ai/`。

```text
raw-materials/  用户投递口；可保留每批原始子目录
originals/     系统保管的原始接收物及版本，不修改字节
library/       面向人的整理目录：主模块/主题/规范文件名

artifacts/     分块阅读、全文报告、质量记录等长期成果
candidates/    待采用的事实和研究结论
indexes/       可重建的检索索引
catalog/       永久资料台账、投递来源和路径历史
```

运行任务数据库、检查点和日志放 `/home/spark/.local/state/inresearch.ai/`；源码按规范放 `/home/spark/code/inresearch.ai/`。原件、台账和成果不进 Git；采用后的结构化知识继续按项目契约进入版本管理。

**上轮准备的 `library/` 是空目录。** 本次将它细化为整理后的浏览入口，今后新增材料的建议投递路径改为 `raw-materials/`；该投递目录本轮尚未创建。此前直接 rsync 到 library 的示例适合当时的静态存放建议，不应再作为常驻收件流程。m5 下载暂存仍使用 `/Users/m5/.local/share/inresearch.ai/downloads/`。

建议把原件身份与整理视图分开：接收完成后，登记、校验并把文件移入系统保管区，保留原始文件名、完整原始目录和投递批次；深读确认后在 library 生成规范目录视图。Spark 本机可用只读原件加符号链接，导出到其他设备时明确解析为普通文件并校验，不能把失效链接当备份。具体视图方式先用样本验证。**raw-materials 清空只代表已接收，待阅读量以台账为准。** 不自动删除原始接收物或解压后的原包；重复投递可以复用计算结果，物理副本处理另记，不凭去重清理唯一资料。

归类与命名规则建议：

- 沿用现行 M01–M15 作为研究主轴；每篇一个主归属，同时打公司/项目、主题、地区、文档类型、年份等标签。跨模块关联通过索引呈现。A5 价值链提案仍未拍板，不借此替换模块骨架。
- 建议展示文件名：`年份_机构_简短标题__文档短ID.pdf`。年月、机构缺失时标未知，不从旧文件名盲猜。
- 原分数与等级完整保留为历史元数据，新评分另记。推荐在筛选视图展示分数，避免分数每变一次就搬文件；若保留旧 `8A_` 习惯，可提供带前缀的导出名。此命名方案仍是设计建议，未批量改名。
- 27B 可以在既定类别内自动分类；新建/合并/拆分目录形成分类体系提案，有版本号和迁移映射，按批处理。遇到新词不自动新造一级目录。
- 工程项目档案、CAD与模型依赖包保留内部相对路径；包内资料建立阅读记录，不逐个拆散改名。
- 改名操作由程序校验并执行：限定根目录、合法分类ID、目标不冲突、源哈希吻合。保存旧路径→新路径、操作ID、结果与回滚记录。模型只产结构化建议，原文中的命令不获得文件操作权限。

## 5. 持久身份、版本与失败恢复

文件名不能再当主键。资料台账至少区分：

| 对象 | 关键记录 |
|---|---|
| 一次投递 | 批次、原始路径/文件名、来源、接收时间、校验结果 |
| 文档及内容版本 | 稳定 doc_id、版本ID、完整 SHA-256、字节数、类型、页数/工作表数 |
| 阅读执行 | 内容版本、阶段/分块、模型与模型digest、提示词/提取器/标准版本、输入输出哈希 |
| 整理操作 | 分类版本、原路径、目标路径、执行/核验/回滚状态 |
| 研究采用 | 真正的 source_id、证据定位、metric_id、实体、口径、时点、核验与采用记录 |

完全相同哈希才可按匹配的阅读标准复用成果；同名异文不得覆盖，标题相近、译本与新版仅建立关联。文档版本不是“文件最后修改时间”。旧库缓存哈希必须经映射解析到来源记录，不能直接写入 `source_id`。

接收优先采用临时传输目录/文件名和完成清单，完成后原子交接；读取时排除 partial、隐藏临时文件与未完成批次。只有时间上“大小稳定”不足以证明百度端已下载完，须核对客户端/传输清单，并在读取前后核查内容一致性。定时对账补偿监听漏事件，目录监听本身不代表可靠登记。

任务按“内容版本 × 阶段 × 分块 × 配置版本”建立唯一执行键。输出先写临时文件，校验后原子归档，再提交状态；崩溃重启可复用已完成分块。文件系统和数据库不能假装在同一事务中，操作日志记录准备、执行、核验、提交，重启时先对账未完成操作，避免重复移动和重复采用。备份恢复也须校对台账、对象和成果之间的引用。

唯一任务键不保证远端推理只执行一次：超时或本地中断时，模型可能已执行，恢复按至少一次处理。HTTP重试沿用网关客户端策略，研究层仅管理有记录、有上限的阶段重跑，避免两层重试倍增。每次尝试使用独立暂存路径，只有当前有效尝试能提交正式成果与状态，迟到结果不能覆盖。

网络暂断、格式错误等可有限重试并退避；密码、损坏、持续解析失败单独进入异常队列，记录原因与恢复条件。异常件不算深读完成，不无限重试占用整机。磁盘不足等共享故障暂停受影响写入并报告，不能标记成功或删旧原件腾空间。

## 6. 长期运行与吞吐量

运行若干周的是受进程管理器守护的服务；每次模型调用仍是边界明确的小任务。第一版建议一个 27B 推理任务在途，CPU 提取适度并行；先复用 SQLite 和标准库，不引入分布式消息系统。

粗读新料与深读积压分开排队，按研究价值、时效、等待时间及预计耗时调度。旧积压保留服务份额并随等待时间提权，新料不会无限插队。只要长期到达量小于处理能力且故障得到处理，积压可逐步消化；否则“全部最终读完”必须先增加能力或改变供料/服务安排，不能靠队列承诺。

优先保护交互任务是计划目标，当前网关并没有实现跨所有调用方的 GPU 全局优先级。第一版在分块边界让出、限制推理并发并观察负载；后续若需硬性资源保障，再建设共享准入机制。不得为抢占研究任务自行卸载其他业务模型。部署前明确与 infra 的模型服务及其他任务共用规则。

每日处理能力须按真实样本测量：文字/扫描PDF、中英文、表格密集报告、超长文和工程附件分层统计粗读、深读、复核耗时与失败率；用预计服务时长而非只用文件数衡量积压。设可用服务时长为 C/日，新料需求为 A/日，已有积压需 B 小时，只有 C>A 时才有约 B/(C-A) 天的清积压估计；这仍受材料分布和重试影响。

处理进度按批次及接收截止日报告，持续进料没有永久的“全库100%”。至少显示：新接收/唯一文章数、粗读完成、深读完成、最老待阅读时间、部分完成与异常数、采用情况、分类返工率、服务时长及磁盘余量。每日资料汇总可由本地服务生成；通知只针对需要处理的故障、重要冲突和阶段完成，本轮不创建提醒或自动任务。

## 7. 可复用能力与必须新建部分

现有 infra 提供统一模型网关客户端、SQLite WAL 队列、单 worker 锁、事务领取、重启恢复及旧执行回写保护。可复用低层机制，具体实现须遵守仓库边界：推理与通用能力归 infra，资料状态、目录语义和研究采用归 inresearch。

现成队列不是永久研究台账：

- 摘要/分类 handler 使用 `fast`，分类只取前 8,000 字符，不满足本轮 27B 完整阅读要求。
- FIFO 队列尚无资料去重、跨阶段依赖、等待时间提权及分块阅读状态。
- 终态 payload/result 默认 14 天清理，即使无人取走也过期。
- 结果导出按 basename 命名，有不同目录同名覆盖风险。

因此需补建长期资料台账、接收对账、分阶段编排、覆盖记录、成果校验、分类操作日志与长期成果归档。任务临时数据可按规则清理，原件/台账/阅读成果不随任务TTL删除；本地原件与数据库不自动包含在现有 Lightsail 备份中，需备份并演练一致性恢复。

infra 当前边界是 Spark 供推理、mini 跑通用文件worker。若本方案落实，需明确新增“Spark 就地处理 inresearch 原件”的职责并更新运行文档；不顺手搬迁 mini 的其他服务或修改 OA 队列。原件放到 Spark 不自动意味着任务已经启动。

## 8. 与研究主项目的接口

永久原件与候选产物留在数据盘。稳定文档ID解析到原件，检索与目录路径可以重建；兼容旧 CSV、sources.local_file 的导出由程序生成，不能反过来拿旧路径当阅读完成凭据。

阅读成果进入候选池后，采用沿用已有口径与 C3 规则。当前 A 档（≥8、sensitive、事实冲突）人审、B 档模型审并抽查、C 档存档规则仍在；本稿没有因“自动归类”取消用户已定的研究采用要求。阅读和文件整理可继续，不被待采用记录阻塞。若 A 档积压形成瓶颈，应单独评估采用标准，不悄悄降档。

不把作者预测变成项目既成事实，不因高分自动生成 current Finding。采用前验证来源外键、指标、实体、单位、口径、观察/发布时间、定位与推导链；主张须回答具体研究问题，并记录与旧结论的关系及可证伪条件。原文页/单元格证据可供审阅端访问，不再局限于 CSV 摘要。

## 9. 分阶段落地与验收（建议次序）

1. **规则与台账样板**：确定单篇阅读产物、完成标准、稳定身份、目录规则和异常处理。导入旧评分为历史判断；无逐页覆盖与原文依据的旧“精读”标签标未验证，不直接豁免新深读。
2. **30–50篇分层样本**：覆盖上述格式/长度/语言，以及旧粗读文章、重复文件和工程包。先验证阅读质量、证据定位和改名方案，再测耗时。模型多跑几遍一致不替代独立原文抽查。
3. **持续性试运行**：小队列连续运行48–72小时，期间投新文件；验证传输未完不读、重复投递不重算、处理中断可续、同名不同内容不覆盖、改名中断可恢复、单篇失败不阻塞其他篇、旧积压仍推进，以及备份恢复。
4. **接入历史与日增量**：按批次迁入百度材料，使用清单核对。长批次处理中也持续接新料，保留旧原始目录和分数的来源；根据实测容量滚动估计时间。
5. **研究积累阶段**：把可靠候选持续用于来源、事实与 Finding 更新；监测矛盾、新版替代与过期证据。检索/RAG 用于找材料，不能替代逐篇深读或事实核验。
6. **长期治理**：版本化分类改进、选择性重读、质量漂移抽样、恢复演练和容量扩展。新模型或提示词只重跑受影响阶段，保留旧成果与更改原因；跨文献专题综合作为额外任务，不取代逐篇覆盖。
