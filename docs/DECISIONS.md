## 2026-09-09：reader 单进程内多线程处理任务

阅读吞吐受限于串行等待模型返回：一个任务领一次、读一次、等一次，GPU 空转。改为「队列所有权不变、进程内多线程」：仍只有一个进程持 catalog 锁（中断回收与对账仍只做一次，第二个进程照旧 `another_worker_owns_queue`），进程内按 `READER_WORKERS`（默认 1，上限 16，或 `--workers N`）起若干工作线程。每线程一条 SQLite 连接，领取仍走 `BEGIN IMMEDIATE`，同一任务不会被领两次；扫描与入库仍留在持锁线程，保持单写入者；`--once` 排空要等所有线程都空闲才收工，因为在跑的任务还会派生下一阶段；任一线程异常停下整个 run 并上抛。默认值 1 表示行为与改动前一致，本条不代表 Spark 已重启生效。

**这不会自动变快**：Ollama 默认串行应答，服务端须设 `OLLAMA_NUM_PARALLEL` 不小于线程数，且「并发数 × num_ctx」的 KV 缓存要放得进显存，否则只是把排队从客户端挪到服务端，或触发模型换出更慢。27B/32k 下先从 2 起步实测。规则写入 Spark 操作手册「并发与吞吐」。

## 2026-09-13：修订链改为整条链，旧版可后录；locator 里点了名的断言者补齐

## 2026-09-14：科智投资额两版判为整体重估；补四处菜单缺口；队列按已读产出降权

**一、科智咨询智算中心投资额 879 vs 1198（差 36%）判为修订，不拆指标。**
判据是比值不是措辞。旧版（深企投 2025-04 转引）自述「2023 同比 +90% 以上」，反推旧版 2022
约 463；新版（科智《中国智算中心供配电系统应用市场研究报告（2025）》）2022 记 629，
629/463 = 1.36，而 1198/879 = 1.36——**两个年份拿到同一个因子**。单年口径差不会在相邻两年
给出同一比值，整条历史被同一因子抬升才会。另外新版自身 1198/629 = 1.905，恰好复现旧版原文
那句「同比 +90% 以上」，说明增速结构没变、变的是基数。
「市场投资规模」与「领域投资规模」的措辞差异不足以拆指标：已验证「新 = 旧 + 基础设施投资」
不成立（2023 879+203.5=1082.5≠1198；2022 463+117.2=580≠629），找不到可指认的口径增量。
读表侧记的 supersedes 保留。
**顺带发现一处真风险**：旧基数上的两条预测（2024E 1014、2028E 2886）仍在库里且无人接替——
预测不要求 supersedes（同一家在两个时点的预测是并列的判断），所以按契约它们是对的，但它们
站在低 36% 的基数上。已在这两条和另两条上写明两版不得混用：把两版放进同一张图或同一段
CAGR，算出来的增速是重估造成的，不是市场发生的。

**二、四处菜单缺口（ada08791f7b0）补齐。**
新增 `dc_power_equipment_market_size`（数据中心供配电设备市场规模，亿/原币，M09），口径维
product_line / service_scope（含不含安装服务差一大截工程费）/ facility_type / currency /
region / basis。`UPS&HVDC` 是独立取值而非 UPS 与 HVDC 之和——科智原文合着给，拆开录等于编。
`ai_compute_market_size.measure` 补「智算中心基础设施投资」，并写明它与「智算中心投资额」是

**三、队列按已读产出降权，不按体裁降权。**
一次 OCP 2025 会议的九份胶片与讨论环节粗筛都是 7 分、读完全是 0 条，却因分数高排在前面，
每轮吃掉一半名额。粗筛分答的是「这份材料讲的事重不重要」，它答不了「这份里有没有可录的数」。
做法：同一家 × 同一年 × 同一体裁为一个批次，已读满 3 份且一条未出的批次排到同覆盖度组的
最后（`barren_cohorts`），`queue` 里报出来。
**不预先给任何体裁降权**——带数的规格书和胶片不该因为体裁被压住，压住它们的只能是同批次的
空手而归；一旦这批里有一份出了数，这个批次立刻不再算空，所以这是能自己纠正的降权，不是黑名单。

出处不明的材料归成同一堆一起压掉，而它们彼此毫无关系（写这条测试时正是这样漏的）。

## 2026-09-14：降权补上目录批次；近似比对的两个盲区；同年预测离群单独扫

读表侧报来三处，两处是上一轮我自己留下的洞。

**一、降权只按机构分批，漏掉成批躺在一个目录里的东西。**

带上它的覆盖范围；新增 `manage.py deep-read resketch`，用已有的唯一当前阅读结果补 sketch，

块哈希，两份这样的文件重合度算作 0。**两条都不在这轮动**：调低阈值会把大量套话相同的材料
判成副本，代价更大；真解决要换更细的表示，是另一件事。已记进 not_verified 与用例。

同一家的多个时点不算多家。**只提示不判定，也不改 `claim_identity`。**

## 2026-09-15（四）：「无署名即无断言者」的边界——直接陈述 vs 转手于无名第三方

上一节写了「插值无署名即无断言者」（ADEME/Bordage 98 TWh 因此不录）。这一节把它的边界划清，
**否则照字面执行会连带杀掉一大类本该录的记录**：行业报告与案例文里大量「研究表明……」
「业内普遍认为……」的数，都没点名出处。

**判据是原文把这个数怎么摆出来的：**
- **原文直接把数陈述出来**（哪怕引的是无名的「研究」）——**写的人就是断言者**，记到该作者／该机构名下，可录。
  他把话说出口，就担了这句话。
- **原文明说这数是第三方做出来的、却不给名字**（「由 JRC 2015 与 2020 值插值得到」而不说谁插的）——
  **没有断言者，不录**。缺的不是值，是没有任何人对它负责：作者明确把它归给了别人，而那个别人不存在于文本里。

配套一条：前一类可录，但 `basis` 不得记「实测」——**无名的「研究表明」不是计量**。
在 `server_cpu_utilization` 的 basis 维注释里写了这条（记「行业调研」并在 notes 标 `[未核]`）。
本轮读表侧录的「传统数据中心服务器利用率 5%～15%」（重庆农商行案例，上下界两条）正属前一类，
署名与 basis 都对，不必改。
