## 部件表 2.0：切到有自己的价格、供应商与交期为止（2026-09-28）

`framework/bom.json` 2.0 是爆炸图的名词轴。切分只用一条规则：拆到有自己的价格、自己的供应商名单、自己的交期为止；普通紧固件合并，关键稀缺件不合并。按此规则 46 条变成 61 条物理部件，另有 1 条软件条目（DCIM/BMS/EPMS）与 1 条设施基型（预制化/微模块）；`kind` 区分 part / software / archetype，只有 part 占尺度。五个尺度用 S1–S5（园区、建筑、机房、机柜、部件），`layer` 键是兼容名，与经济模型的五类变量无关；`system` 只取叶子系统（设施、电力、冷却、控制与软件，以及 IT 下的计算、内存、存储、网络），见下节「一个骨架」。用户 2026-09-28 批复的切分：通用服务器与加速器服务器分两行，BMC 与 CXL 内存单列，机柜配电条并入 PDU 不再拆，小型模块化反应堆登记为 emerging，软件条目进目标表。

站点权利与配额（土地、水权、电力配额与并网、天然气管道接入、网络接入、许可）不可采购，登记在 `framework/site_rights.json`，每条写明落在哪几类变量；因子树用 `site_rights` 字段引用。合同（PPA、租约、算力合同、融资）不进这两张表，按主体类事实处理。

部件 ID 是稳定锚点：存续的部件保留旧 ID 只改名；拆出的新部件用新 ID 并记 `split_from`；被拆分或移出的旧 ID 写进 `aliases` 指向去处；图谱 3.0 由骨架生成，旧 ID 作为目标对象的 `aliases`（不再有隐藏节点与 `redirect_to`），接收端把旧快照里的旧 ID 折算到骨架节点，网页、3D 场景与产品目录经别名解析，不因重切失效。`data/products.json` 的 `bom_parts` 按产品线名重映射到新 ID。校验：`validate --strict` 检查 kind、尺度、系统、公司、别名去处与权利表；`tests/unit/test_bom.py` 固定上述决定。

## 一个骨架：第一层按系统，系统内按链路，尺度是属性（2026-09-28）

用户采用：一个骨架、一套顶级系统、一个 mindset，所有组件、爆炸图、采集都对齐到它。树只有一棵：数据中心 → 五个系统（设施、电力、冷却、IT、控制与软件）→ IT 再分计算、内存、存储、网络 → 系统内按能量流链路 → 部件。`bom.json` 的 `systems` 登记父子关系与链路顺序；每个部件的 `system` 只取叶子系统，并带 `chain`（系统内链路段）与 `chain_order`（段内序号）。链路：电力为电网接入 → 变电 → 发电与储能 → UPS → 配电 → 机柜与板级供电；冷却为排热 → 冷水与 CDU → 机房与机柜 → 芯片级；设施为土地与建筑、消防安防；IT 四个子系统各一段；控制与软件一段。边界件按能量流位置归属，不按厂商：储能归发电与储能，电源架、PSU、VRM 归机柜与板级供电，冷板归芯片级，歧管与快接头归机房与机柜，燃料储运跟发电。判据只有一个，新部件不需要讨论。

尺度（S1–S5）、模块、尺寸都降为部件的属性，不再作为任何视图的第一层。爆炸图（`bom.html`）第一屏是五个系统，IT 展开四个，系统内按链路排，尺度是可切换的第二排法；园区 3D 的领域视角从 `systems` 生成，进入一个系统后镜头沿链路依次飞入；研究图的 `hardware_domains` 与生态研究入口按同一顺序；dashboard 矩阵五行、IT 可展开四行，系统节点的部件表按链路分段；目标表的部件级行按系统与链路顺序排，采集优先级沿链路上游先走。校验：物理部件必有 `chain`，`chain` 属于其系统，同一链路内序号不重复，部件不得挂父级系统。

## 骨架的三个补充（2026-09-28 采用，与图谱 3.0 同批实施）

1. **建设阶段是部件的第二个属性。** 能量流链路（`chain`）回答"由什么组成"，不回答"先建什么"。`bom.json` 每个部件与每条站点权利加 `stage`：权利与审批 → 并网与外线 → 土建与壳 → 机电 → IT 进场 → 调试与上架。根节点"它怎么建"按 `stage` 排，采集页默认排序也按它；因子树加时间因子 `time.build`（建设期、门槛等待、审批期、排队年限），目标表由它生成工期与排队行。
2. **部件级运行行。** `part_fetch.json` 的数据类别加 `operation`（额定功率与功率份额、效率曲线或 PUE 贡献、寿命与 MTBF、上架与利用率），目标表生成部件级运行行；此前运行类只有因子级 10 行，四个 IT 子系统与控制在运行列没有任务可派。
3. **登记表加两列。** 价格库、事实库、产品库、公司库、指标表、知识库每条记录加 `node`（root / system:x / part:x / site:x / actor:x）与 `variable_class`；产品库由 `bom_parts` 派生 `system` 与 `chain`，内存单列。这是"数据从哪来"能回答、六队交付物能进目标行状态的前提。

## 三条判据（2026-09-29 采用，依据 docs/reviews/2026-09-29/skeleton）

1. **对象类型 actor 不等于变量类 5。** 图谱里的"主体"是对象类型（`companies.json` 的 248 家公司，`node = actor:*`）；五类变量里的"主体"是数据类别（谁持有、谁供应、谁付费、谁签约）。一条变量类 5 的记录挂在部件、权利或根上并引用一个 actor，不挂在 actor 自己身上；只有公司库自身的记录允许 `node = actor:*` 且 `variable_class = 5`。节点页第五列显示"谁供应 / 谁持有"，主体页显示"这家公司"，两页语义不同，不互相冒充。
2. **建设阶段 `stage` 是排序键，不是变量类。** 时间类（变量类 4）的变量是交期、工期、排队、许可年限；`stage` 只回答"先建什么"，给"它怎么建"读法与采集页排序用。系统的时间列取部件交期最大值（关键路径），不由 `stage` 派生任何数。
3. **只有需要被追问到底的东西才成为对象。** 图谱对象只有六种（根、系统、链路、部件、站点权利、主体）。项目、合同、租约、融资是主体与部件 / 权利之间关系上的事件，作主体页附表与事件卡，不成对象；价格序列按 `series_id` 挂在部件或权利上（`knowledge/nodes.py`）；地区是统一模型的预设，不是对象。新增对象类型须先改本条与 `graph.py` 的校验，再改数据。

键名（2026-09-29）：`bom.json` 的尺度键叫 `scale`（S1–S5，顶层 `scales`），旧模块键叫 `legacy_module`；`layer` 在骨架文件里不再出现，只在目标表以外的外部 feed（inews `layer_tags`）作变量类的兼容名。`validate --strict` 拒绝旧键。

## 模型表达

骨架的每个节点（根、系统、链路、部件、站点权利、主体）只有一个身份；空间包含、装配、供电、冷却、网络、控制、制造、持有、运营和使用是有类型的关系，不是第二棵树。

读者沿系统 → 链路 → 部件深入；尺度（园区、建筑、机房、机柜、部件）是部件属性，用于筛选不用于分层。实际装配允许不同深度；室外设备不强制经过建筑层，外部工厂不是机柜子件，CDU 服务多个机柜不等于它拥有这些机柜。

每条关系写明类型/实例、时点、配置、方向和证据；接口注明端口、介质/电压/协议、容量及工况。类型、厂商型号与真实资产分别登记，不从通用模型推断具体站点。

## 每个节点都有问题、材料和成果

每个节点按四问组织研究（它值多少、由什么组成、怎么影响账、数据从哪来缺什么）；问题、证据和任务是独立记录类型，各自挂到骨架节点与变量类。产品采用不同研究深度，不适用项说明理由。每份材料与节点的关联应定位到页/节/表/图/单元格，标直接研究、实测、背景、仅提及或反证。上层有一篇资料，不表示全部下层已研究。

3D geometry 只引用研究对象 ID，不在脚本里维护第二份事实。点击节点可到结构、方案、参数、公司、原文、判断与缺口；从材料也可反查支持的问题。

视觉精细度、身份可信度、资料完整度与研究状态分开。标明概念示意、官方参考设计、项目设计、竣工核对或运行核对；内部未知不补猜。成熟度、供应紧缺、技术替代和证据质量各自记录，不共用一个永久 status。BOM 数量与采购套件、父项含价与子项成本、冗余设备与运行容量分别统计。

## 协作与变更

- 旧模块 M01–M15 自 2026-09-28 起只是兼容属性（`legacy_module`），不再是维护单元、归档路径或任何视图的分组；每个节点/问题有明确 owner，合并按现有采用规则。
- 任务只来自目标表（`tco_targets.json`）的目标行；研究问题按节点与变量类挂在第四问，不再单独派工；获取文件只是子任务完成，不能直接关闭研究问题。
- 派工以目标行 ID 为对象；`reports/workorders.json` 的模块缺口工单自 2026-09-28 起不再生成（实施见 DECISIONS 的迁移顺序，接口改造完成前旧文件只读保留），负责人记录按稳定目标行 ID 保留。
- 同一事实一个身份、多处使用；变更登记影响面并触发下游复核。并行工作使用独立分支/工作树，按记录 ID 合并。
- Git 保存源码、声明与采用后的结构化知识。原件、数据库、阅读成果和 PDF 等运行产物不进 Git；已有用户批准的 3D 小体积资产例外继续遵守来源与许可登记。
- CODEOWNERS 用于提出评审责任，实际分支保护与权限以托管平台配置为准；文件中写了 owner 不代表已具备强制权限隔离。
- 新分类或关系先形成有证据、边界、映射与版本的提案，再登记生效；模型不根据每篇标题创建一级目录。

## 落地验收

先完成一条有官方材料的贯通样例，将空间/装配、电热数据、主体交易、负载与证据连通，未知保留；验证重复实例、父子循环、接口错连、单位/工况、原文定位与反证回流。再沿其余系统与链路扩展。研究质量与资料可复查程度决定深化优先级，不以空节点或几何数量作为完成度。


## 视觉资产的内容身份与采用（2026-09-14）

`web/assets/models/manifest.json` 是视觉模型唯一发布登记。schema_version=1，file 与 sha256 绑定确切 GLB 内容；candidate、adopted、rejected 分开。仅 adopted 且 page 匹配的条目进入场景；adopted/rejected 有明确决定依据。现有样例沿用既有不采用记录，保留文件供选型参照，退出场景自动加载。此视觉采用不产生研究证据、事实或物理身份认证。

来源页与许可/署名、GLB 2.0 自包含、单文件不超过 10 MiB、有限且有效的变换共同构成准入。materials.model_assets 为共享校验；workflow.model_assets 为作者工作区导入用例；下载只创建 candidate，同名新内容拒绝覆盖，版本用新文件名及新的审阅决定。下载器不能绕过许可要求；不能根据第三方模型的网格数或命名宣称已具备真实部件拆解。

模型比较台显示全部已登记身份，参数只过滤登记内的文件；场景 API 投影只给出已采用条目。静态文件也由同一登记解析。GLB 文件存在不等于已登记，已登记不等于已采用，已采用不等于研究已核验。具体流程在 ADD_3D_MODEL 操作指南，历史自动上传/登记即上线说明退出。

## 计算芯片目录（2026-10-02 补充）

按具体产品区分 CPU、GPU、其他计算加速器；分类投影与原厂 navigation / taxonomy 并存，不改写原厂目录。芯片、板卡、模组、整机/平台、系列/目录、IP 与待核验形态分别计数；成品 CPU/GPU 不包含 ARM IP、网络和配套芯片。Gaudi、昇腾、寒武纪与燧原计算产品归其他计算加速器。海光 DCU 按型号核验，软件兼容性、公司名和 DCU 缩写不证明具体架构；未核验留空。

公司身份复用 `data/companies.json.records[].company_id`。`huawei-kunpeng`、`huawei-ascend`、`hygon-dcu` 保留既有 ID，`entity_type=product_line`、`parent_company_id` 分别指向华为、华为、海光；不重复建公司。中国厂商筛选用公司表的总部国家（CN / 中国），不表示制造地或国产化程度。产品 `parent_id` 仍是产品/系列关系，与母公司关系分开。

2026-10-03 补充：板卡与 OAM 等模组分别计数。板卡/模组使用芯片的关系仅在官方原文明确对应时登记；关系目标为同公司同批目录中的芯片实体。不能把板卡显存、带宽、功耗赋给裸芯片；系列名与容量配置没有可订购料号时不自动当成具体 SKU。
