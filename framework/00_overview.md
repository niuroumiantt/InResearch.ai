# 研究框架总览 v2 - 全行业研究与兼容模块

> CURRENT · 2026-09-12。规则归属与替代关系见 framework/CURRENT.md。

> 2026-09-06 用户采用生效。完整依据：[研究架构 v2](../docs/reviews/2026-09-06/RESEARCH_ARCHITECTURE_V2.md)。本文件定义当前的五视角与局部划分；代码与服务是否已部署须另查验收记录。

当前机器执行入口：`research_graph.json`（对象与有类型关系）、`research_questions.json`（稳定问题与验收）、`data/research_knowledge.json`（正式文档/证据/陈述/回答）。Spark 结果进入候选快照，不能自动改写正式采用记录。研究工作台为 `research.html`，两个 3D 使用同一节点 ID；旧模块文件与 Finding 按兼容视图保留。

## 目标与五个视角

研究整个数据中心行业及上下游，形成独立解释原理、比较方案、复算验证、诊断约束与交付判断的能力。200GW、投资周期和 Token 经济是重要专题，不能替代通用 IT、工程运行、可靠性和生命周期研究。

| 视角 | 对象与问题 |
|---|---|
| P 物理与空间 | 空间、设备、装配，以及关联的产品线、型号与具体实例 |
| F 系统与接口 | 电、热、数据、控制、端口、依赖与故障域 |
| V 产业与交易 | 设计制造、交付、持有、运营、使用、付款与风险 |
| D 需求与工作负载 | 应用、服务、负载、部署策略与资源需求 |
| R 问题与证据 | 问题、原文、数字事实、非数字陈述、判断、模型与任务 |

地域、时点、配置、生命周期、法规与可持续性是贯穿条件，也必须有问题与维护责任。类型、厂商产品线、具体型号和资产实例分开；P/F/V/D/R 不与项目成熟度 L1-L9 混用。

### 浏览目录与产品库

P 的浏览目录按园区与资源接入、建筑与安全、机房与设施、机柜与整机、内部部件分五组，再按层内设备类别展开。目录由 `research_graph.json` 的 `navigation` 声明；P 内每个对象有一个浏览位置。F 按已登记的系统成员展开，同一对象可服务多个系统。切换视角只显示该视角明确登记的对象；R 汇总各类研究对象，并按家族分组。

浏览位置用于查找，不表示设备实际安装层级、空间包含、装配归属或公司的唯一业务角色。这些事实仍由带类型关系、适用配置和证据表达。BOM 的旧尺度作为兼容导航，运维软件以设施配套入口保留其软件类型；不因此成为物理资产。

产品库连接路径是「部件类型 → 厂商或厂商组的产品线 → 具体型号资料 → 经核实的资产实例」。现有 `data/products.json` 的 175 条为产品线记录，不能当成 175 个 SKU 或实际资产。P 依据明确的 `bom_part` / `bom_parts` 映射浏览产品；F 沿系统及装配关系提供关联目录；V2 提供制造、集成与分销的产品目录入口，不以此给公司作唯一分类。D 的工作负载须另有用途或部署证据才能关联硬件，不能凭相同模块自动归入。

产品资料计划、历史索引、当前可用原件、完整阅读和采用证据分别记录。`todo` 计划不算下载；历史登记不证明当前文件可访问，更不证明内容已被采用。产品目录的显示与研究证据完成度分开计数。

## 局部 MECE 与单一身份

- 先限定对象、配置、范围和时点；同一层只使用一种划分标准。全集和未知项显式记录，不宣称穷尽所有未来形态。
- 空间包含、装配、功能连接、供应、产权和运营是不同关系。一个实例在同一时点的同一装配视图只有一个直接父项，可服务多个系统。
- 事实和对象各有稳定 ID；一个维护责任人、多个关联用途。公司可有多个带时点的业务角色，不能复制资产计容量或重复加总供应链收入。
- 旧 ID 不复用，变更有版本和映射。文件路径、分数、显示名不是材料身份。

## 研究契约与引用

每个节点按 [07 产品生态规范](07_product_ecosystems.md) 的九主题组织研究；总览为交付视图，问题、证据和任务为独立记录类型。产品采用不同研究深度，不适用项说明理由。关键问题使用稳定 question_id，声明范围、所需证据、验收、责任人与依赖。

任何模块可引用其他模块的事实或结论，但必须记录 record/Finding ID、版本或修订时点、适用口径和依赖，保留支持与反证。来源修订、配置变化、冲突或到期时，检查下游答案、模型和交付是否需要复核。M15 统筹综合，不垄断跨域推理；历史“领先 12-18 个月”等必须作为可检验判断维护，不能成为分类公理。

数字继续使用 metric/value/unit/caliber/as_of 契约；定义、规范要求、结构关系、机制、事件、测试、预测和假设采用有身份、类型、条件和原文证据的陈述。未接通相应 schema 前保留候选，不挤入数值字段，不把作者声称当作已证实。

## 双向研究与完成度

- 从上到下：边界 → 问题 → 所需证据 → 对照已知 → 缺口任务 → 获取/实测/核验 → 判断与交付。
- 从下到上：原件 → 配置的研究模型粗读 → 每篇深读 → 对象/接口/陈述候选 → 原文核验与 C3 采用 → 回答或新问题/框架提案。
- 每轮冻结 scope_version 与问题分母；对象覆盖、证据覆盖、答案状态、阅读完成、可复现交付分列。关键问题未通过要显示缺口，不能以材料数或平均分掩盖。

## 保持不变的纪律

现行 `01_data_standards.md`、`02_knowledge_format.md` 的容量/用电/金额/需求模型边界、L8+ 当期供给、官方未披露容量不推算、跨中外口径、独立核验与 C3 采用要求保持。自动深读不自动创建 current Finding；数据只留不删，原件不随缓存或任务 TTL 清理。

## 实现与扩展边界

研究定义、原文阅读、知识采用、任务交付、推理适配与操作界面分别有明确责任。新增对象/关系/问题先修改声明及校验；新增研究用例在 Python 领域入口实现，再由网页或 CLI 调用。新增模型只扩展统一配置或推理适配器，不复制评分、采用和任务状态机。新增页面复用导航、外观和接口，不在浏览器重算一份派工集合或报告有效状态。

当前共享入口：`inresearch.knowledge.registry` 计算研究快照、当前任务和采用资格；`inresearch.delivery.report` 为网页与导出提供同一内容集合；`inresearch.adapters.models` 提供配置化推理；`inresearch.materials.records` 提供语料当前观察与有效判定；`inresearch.storage.moves` 统一物理移动与恢复。HTTP 与终端只是这些用例的入口。专用 M4 预览/文件整理与 Spark 全文/C3 流程按各自 scope 保留，不能因代码相似抹平原件权限或阅读承诺。

新代码不扩大兼容 Finding、旧工单和旧 CLI 的规范地位。只有规范中声明为当前的源决定行为；历史记录继续保留身份和转向。若完整任务 API、受控重读或 Spark 接口尚未实现，应直接标明，不在 UI 伪装为完成。

## 框架变更

新词先判断别名、型号、实例、关系或方案条件，再考虑新增类别。边界变更须有理由、来源、受影响问题/对象、旧新 ID 映射、版本、生效日期与复核记录；正式声明与实现同步，不能在单次阅读中无记录造目录。旧资料身份与阅读结果保留。
