# inews.today 单仓架构与演进路线

## 结论

合并已经完成：`inews.today` 是唯一代码库，同时包含公开快讯、认证以及各正文来源的
原文采集、独立原文页和统一 Dashboard。各来源共享协议、编排、存储、
评分和发布纪律，但继续保留独立页面；只有 Dashboard 合并。旧独立仓库不再是
运行依赖，可以不存在。

## 已执行

- Python 包、CLI、日志标识与 LaunchAgent 已统一为 `inews`，不再保留旧项目名称的
  第二套入口，避免新旧品牌继续永久并存。
- 各来源的小时任务共用 `tools/hourly.sh [site]`；锁、输出、备份和
  发布目标由一个小型来源配置选择，执行纪律只有一份。
- 新增明确的 `SiteAdapter` Protocol 和注册时校验。以后接入来源仍然可以写成小模块，
  但缺字段会在启动时一次报全，不会在采集半小时后才撞到隐式属性错误。
- 跨库 dashboard 增加正文覆盖率、积压和最后运行状态，并为窄屏表格提供横向滚动。
- 台账、跑批记录和正文存档改用同一个原子 JSON 存储层；关键状态写入时保留上一版，
  主文件损坏可自动恢复，两份都损坏则停止运行而不是拿空状态覆盖历史。

## 本轮能确认的事实

- 站点差异已集中在 `inews/sites/`，通用编排不应出现站点名分支；这个方向正确。
- 原始正文、台账、跑批记录与发布 HTML 已分层，发布物可由正本重建。
- dashboard 已能展示单库健康、正文覆盖、失败原因、召回效率和跨库摘要。
- 静态页面通过本机 loopback 服务触发抓取；动作白名单、来源白名单和单任务锁是必要边界。
- 直接执行 `pytest` 曾无法导入本地包，而 `python -m pytest` 可以；测试入口不一致会让
  CI、编辑器与开发机得到不同结论，本轮已统一。
- dashboard 原先只看「最后一轮是否成功」。调度器停摆不会产生失败记录，因此一个数天前
  的成功仍显示绿灯；本轮已把超过三小时未运行也判成红色健康告警。

## 现行架构

```text
collectors (FT / Bloomberg / CNBC / WSJ / Reuters / Axios / future sources)
              │
              ▼
        normalized article schema
              │
       ┌──────┴──────┐
       ▼             ▼
 private archive   public projection
 body / ledger     metadata / summaries
       │             │
       └──────┬──────┘
              ▼
       one site renderer + one deploy
              │
       timeline / libraries / dashboard
```

实际单仓目录：

```text
src/                      # 公开快讯、认证、API、调度与质量闸门
web/                      # 公开时间线与主站 Dashboard
inews/                    # 各来源适配器、采集、存储、评分与静态渲染
tools/                    # 各来源共用的小时任务、备份、发布与本机控制
tests/ + test/            # Python 订阅链路与 Node 主站回归
out/<SOURCE>/             # 各来源独立页面；正文正本在不发布的 data/ 下
out/DASHBOARD/            # 唯一跨来源 Dashboard
```

## 后续工程债

### P0：发布与数据正确性

1. 定义带 `schema_version` 的 Article、Run、LibrarySummary JSON Schema；所有写入先校验，
   renderer 只读契约，不读采集器内部结构。
2. 合并部署为「生成到临时目录 → 完整性检查 → 原子切换软链接」，避免两个仓库分别 rsync
   时出现导航已更新、目标页尚未到位的半发布状态。
3. 为每个库记录 `started_at`、`finished_at`、`duration_seconds`、阶段状态和最后成功时间；
   dashboard 的健康应由新鲜度、退出状态、正文失败率三者共同决定。
4. 保持私有正文与公开投影物理隔离，并在发布测试中断言 `data/`、cookie、日志和错误原文
   不会进入公开目录。

### P1：后台从「报表」升级为「决策面板」

1. 顶部只保留需要行动的四项：库新鲜度、失败率、积压与预计清空时间、最后一次异常。
2. 跨库表增加成功率、运行耗时、每页新增、最近成功时间，并明确每行快照时间。
3. 增加 24 小时 / 7 天窗口，而不是只报全生命周期累计；累计数会掩盖当天解析器失效。
4. 每个异常给出固定下一步动作：刷新登录态、检查选择器、手动修复、查看对应运行日志。
5. 区分采集健康和内容健康：前者看任务、解析、正文；后者看来源覆盖、重复率、主题变化。

### P2：简化代码与内容逻辑

1. 用 `SiteAdapter` Protocol 取代隐式模块属性约定，启动时验证每个站点是否完整实现。
2. 将 HTML 大字符串逐步拆成小型组件和语义 view-model；统计计算一次后同时供页面与测试使用。
3. 将关键词、专题来源和内容标签拆成不同字段，避免分析时把召回手段误当文章主题。
4. 对标题翻译保存模型、时间和源标题哈希；源标题变化时才重译，避免陈旧译文。
5. 用固定 fixture 做跨仓库契约测试：同一份数据在时间线、单库清单、dashboard 中的篇数、
   状态和链接必须一致。

## 验收标准

- 一条命令运行全部测试，一条命令生成完整站点，一次原子操作发布全部页面。
- 任一采集器停跑超过约定窗口、解析结果突降或正文失败率越线，首页与后台都明确告警。
- 任一数字能追溯到带时间戳的输入文件；缺数据展示「未知」，不展示伪造的零。
- 新增来源只实现 adapter 与 fixture，不修改通用编排、导航和 dashboard 分支。
- 公共发布目录的自动扫描确认没有正文正本、凭据、内部日志或敏感错误信息。
